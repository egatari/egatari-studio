# Egatari Viewer

English | [日本語](viewer.ja.md)

Egatari Viewer is a web app that opens an [Egatari](https://github.com/egatari/egatari-spec) file (.ega.html) on the viewer's device and plays it. It is meant to live at `https://viewer.egatari.org/`; added to the Home Screen it is called **Ega Viewer**, with the え icon (the Egatari mark; Egatari Studio's own icon is す). **It is not deployed yet** (see [Deploying](#deploying-for-the-maintainer)).

For people handing out files: [Opening an Egatari file on iPhone and iPad (Egatari Viewer)](viewer-sharing.md).

It exists because a single file cannot always be opened as a web page:

- iPhone and iPad cannot open a local HTML file from the Files app;
- some Android file apps hand the browser a `content://` address that does not work well;
- chat apps (Slack and others) fail to preview large files.

The viewer chooses the file in the page (or shares it to the installed app on Android). The file is read in the page and is never uploaded.

## Using it

- **Open a file**: the 「ファイルを開く」 (Open a file) button, or drop a file on the page. Only Egatari files play: a page whose `deck-meta` is not an Egatari one is refused. The bar shows the file's title and whether it is an 「Egatari ファイル（編集可）」 (editable: an Egatari file with its archive layer) or an 「Egatari ファイル（再生専用）」 (play-only). Both play the same; editing is done in Egatari Studio.
- **Created and edited by**: when the file records edits by other people (`metadata.edits`, spec §3.6.1), a line under the title says 「作成：<creators> ／ 編集：<the most recent entry> ほか n 件」 (Created by … / Edited by … and n more); an entry without a name reads 「元のファイルから編集されています」 (Edited from the original file). Pressing it opens the list: creators, every edit oldest first, copyright and license. The Viewer reads them from `deck-meta` (else the index `metadata`), so they show whatever player the file carries (a tier A save that adds edits keeps the file's player). A file without edits shows no line.
- **Recent files**: files you open are kept in the browser, under the notice 「この端末にだけ保存されます」 (stored on this device only), in OPFS (the origin private file system) or, where a page cannot write OPFS (older Safari), in IndexedDB. Up to 10 files; each can be deleted, or all at once; the checkbox 「開いたファイルを「最近のファイル」に保存する」 turns keeping off. **「共有の端末」 (Shared device)** is for a device several people use, such as a school iPad: it turns keeping off and deletes the files already kept, and the choice is remembered on the device. It is off by default (`SHARED_DEVICE_DEFAULT` in `play/main.js`, one constant to flip), so one line right under **ファイルを開く** (Open a file) says what happens to the file being opened: 「開いたファイルのコピーを、この端末の「最近のファイル」に 10 件まで保存します。」 (or that nothing is kept, with keeping off or on a shared device), with a link to the 「共有の端末」 switch and, once copies exist, 「すべて削除」 (Delete all, the same confirmation as the button in the list). Nothing is uploaded anywhere. Once the first file lands in recents (keeping on, shared device off), the page asks once per launch for persistent storage (`navigator.storage.persist()`, errors ignored, never awaited before playback continues) so that WebKit (Safari 17+, iOS 17+) stops evicting the origin on its own; under the notice, a line shows the browser's actual answer (`navigator.storage.persisted()`), hidden in shared-device mode or with nothing kept.
- **Install**: the page is a web app (manifest and service worker; `name` "Egatari Viewer", `short_name` "Ega Viewer", and `apple-mobile-web-app-title` for iOS). On Android and desktop Chrome, install it from the browser menu; on iPhone and iPad, Share → Add to Home Screen. Once it has been opened, it opens offline. iOS and iPadOS have no install prompt, so on iPhone and iPad, in a browser tab (not from the Home Screen), the start screen shows one line with iOS's own labels (Safari: Share → "View More" → "Add to Home Screen" → "Add"; checked on an iPad on 2026-10-27) until it is dismissed with × (remembered on the device). In Chrome on iOS (CriOS) the steps are Share → "View More" → "Add to Home Screen" with "Open as Web App" left on (that makes it standalone and offline; checked on an iPad on 2026-10-27). On Android, when the browser fires `beforeinstallprompt`, the line carries an Install button that calls `prompt()`; it hides after installing and when running standalone. A PC shows neither: there the .ega.html plays in the browser itself.
- **Share to it (Android)**: the installed app is a share target. Share an .ega.html from the Files app or a chat app and choose Egatari Viewer.
- **Language**: Japanese first; the 「English」 button switches (remembered on this device).
- **Reopening where you left off** (player spec P5 and P8): the Viewer keeps the last step you were at for each file (its docId, or the file's SHA-256 when it has none) on this device only (`localStorage` `egatari-viewer-resume`, the newest 50 files; `play/resume.mjs`). When the file is opened again, the player's `ready` lists the timeline and the Viewer answers with a `seek` to that step, and a notice over the top of the file says 「前に見ていた所（<slide title>）から開きました」 (Opened where you left off) with 「最初から再生」 (Start over) and ×; it goes after 12 seconds. 最初から再生 goes back to the first step, and at the first step nothing is kept. Not on a shared device (turning 「共有の端末」 on deletes the kept positions, and so does deleting all recent files), not for a file with a Live (the host leads), and not for an older player that sends no `ready`. A kept step the file no longer has is ignored. **Preferences** go the same way (Player P5 and P8 `prefs`): when you change the layout, the book's text size or background, or captions and their size in the player, the player reports them and the Viewer keeps the layout per file and the others once for the device (`localStorage` `egatari-viewer-prefs`, `play/prefs.mjs`), and sends them back right after `ready`, to a player whose `ready` lists the `prefs` command. Not kept on a shared device; turning 「共有の端末」 on deletes them. `tools/test-viewer-resume.mjs` (Chromium and WebKit) checks these.
- **Printing and attachments are not in the Viewer.** The file plays in a sandboxed frame that may not open a print dialog or save files (see [How the file is kept apart](#how-the-file-is-kept-apart)), so the Viewer cannot print the file and cannot save a file's attachments (what the Viewer prints is the learner's notes as a PDF: [Export and read in](#export-and-read-in)). To print or save a PDF, open the file in Egatari Studio and use 「スライドを印刷・PDF に保存」, 「本を印刷」 or 「台本を印刷」 (Print slides / Save as PDF, Print book, Print script). To save an attachment, open the file directly in a desktop browser: the file's own player lists its attachments and saves them. The Viewer will save attachments once the player can hand them to the page (`saveAttachment`, planned for Egatari Player 1.1).

## Markup (highlights and recall)

A learner can highlight text in a file's book and on its slides and practise recall on it (stage 1 of the markup plan; stage 2 added the slides' text, [notes](#notes-per-slide-and-per-section-of-the-book) and export, handoff #107). The words follow `docs/terms.md`: マークアップ (Markup), ハイライト (Highlight), 暗記 (Recall), 一覧 (List).

- **Highlight.** Select text in the book: a small window with three colours appears: with a mouse, just above the selection; on a touch screen, docked at the bottom edge of the book's pane with 44 px buttons (at its top edge when the selection is near the bottom), above anything of the file's own found there (the player's bar or captions, found by asking what lies under the window's corners) and above the Home Screen app's bottom safe area. It is named 「選んだ字に色を付ける」 and has × to close it without clearing the selection (it does not come back for that same selection). iOS puts its own menu (コピー・調べる …) right above the selection when there is room and right below it otherwise, so on an iPad any place next to the selection was covered in one of the two cases (2026-11-09); the edge away from the selection is free in both, yellow, pink and blue. A tap on a highlight opens the same window to change its colour or 消す (delete) it. The colours are fixed pairs for each background of 文字と背景 (white, sepia, black), chosen so that every pair stays apart under simulated protanopia, deuteranopia and tritanopia with text contrast ≥ 4.5:1 (table below). **Painting** is the markup module's own layer: one element (with a shadow tree, so the file's styles cannot reach it) added inside the book's scrolling box (`.dx-body`, which is `position: relative`), after the article. The highlights are boxes there, drawn per text node, blended with the text (`mix-blend-mode: multiply` on white and sepia, `screen` on black), so they scroll with the text with no delay and let taps and selections through. Only the highlights near the screen are drawn (the visible part of the book and half a screen before and after; the first one is found by halving the list in reading order), and scrolling past that margin draws again. They are drawn again whenever the text moves without a scroll: font size, line spacing, background, a pane resize or rotation (a ResizeObserver on the article and its scrolling box), fonts, images or math loading late, and a `<details>` opening. **Cost**, measured at the 2,000 cap with the highlights packed into the small test book (about 900 of them near the screen on a phone): a redraw after a font change takes about 42 ms in WebKit and 9 ms in Chromium (`tools/test-viewer-markup.mjs`). The layer is hidden in print (stage 1 prints the book as it is) and holds no text, so a copy of the book copies the book's text only. Text contrast under the blend stays ≥ 4.5:1 in all nine pairs (lowest: yellow on black, 4.9:1). The book's text and markup are never changed. Not the CSS Custom Highlight API: on an iPad (2026-11-09) Safari did not paint it on ruby bases, and left the old colour on screen after a highlight was recoloured or deleted until something else repainted.
- **Markup** (the button at the right of the header, next to ファイルを閉じる; below 760 px only its highlighter icon) swaps the header's contents for the markup bar: 暗記, 暗記する色 (while 暗記 is on), 一覧. Pressing it again, or Esc (also in the file), goes back. The bar stays in the header and keeps the header's height, so nothing appears over the file's frame and the frame never moves (see Live: taps are lost on chrome that appears over the frame). The button shows for a file that takes highlights (one with a book or slides; a tool that depends on the content shows only when it can be used, like the player's bookmark buttons; the owner's iPad check 11/22; the file's frame reports this in `hello {supported, article, shown, slides}`). From stage 2 the slides' text takes highlights too, so the button shows for a file without a book, and 暗記 and 一覧 are there with the slides alone. Only when highlights cannot be made at all (an old browser) does the bar say 「このファイルでは、ハイライトは引けません。」.
- **暗記 (Recall)** hides the text of the chosen colours (暗記する色, all by default; each switch is named 「暗記する色：黄」 and so on) under an opaque band of the highlight's colour; a tap reveals that one highlight, which keeps its colour. **Keyboard:** each hidden highlight has a button in reading order (Tab), named 「隠したハイライトを表示（黄）」; Enter or Space reveals it and the focus moves to the next one. The keys are taken before the file's player, which would use Space for the next step. The buttons sit in the module's layer after the article, so Tab reaches them after the book's own links (accepted for stage 1); among themselves they follow reading order, and the browser scrolls a focused one into view. The bands themselves are aria-hidden: a screen reader reads the text anyway. The bands are in the same layer and also cover emphasis marks (傍点) and the reading of a highlighted ruby base (otherwise the furigana gives the answer away). A display equation gets one band (and one box of colour), and pieces on one line are joined into one box, so math is not covered symbol by symbol. Closing the bar ends 暗記 and shows every colour again.
- **一覧 (List)** groups the highlights by section; a tap jumps to one. Per colour: a name the learner may give it (kept on this device for every file), この色だけ表示, この色を非表示 (for this session only) and この色をすべて削除, confirmed in the page (「黄のハイライトを 12 件削除します。元に戻せません。」). Highlights whose text is gone after the file was revised are listed under 「場所が見つからないハイライト」 and are never deleted on their own.
- **Anchors** follow egatari-spec annotations.md (Highlight record): the section's `data-section-id` (`""` outside any section) and a text quote (exact up to 1,000 characters, prefix and suffix up to 32) of the rendered text without ruby readings or KaTeX's hidden MathML. Re-attaching: in the section, the best prefix/suffix match; then the whole article; otherwise kept as not found. Font size, line spacing, background and page layout do not move them; a file rebuilt in place is anchored again. **Ruby:** a ruby segment (a run of base text and the `rt` after it: the whole word when one reading is written over it, each character when readings are per character) is one unit. A selection that starts or ends inside a segment's base is widened to the segment's edges before it is stored (the live selection is left as it is), and the base and its own reading are painted and hidden (暗記) as one box. A record made before this rule, ending inside a segment, is widened the same way once it is re-attached and saved back with the same id, colour and created (the frame sends `widen`; the page takes only a quote that holds the old one).
- **Storage.** One record per `docId` in IndexedDB `egatari-viewer-notes`, on this device only: never in the file, never sent anywhere. `madeOn` records the version (`fileSha256`, and `sourceSha256` from an editable Egatari file). An editable Egatari file and its play-only copy share the record. The first saved highlight asks for persistent storage, as Recent files does. On a **shared device** nothing is saved (the bar says 「共有の端末なので、ハイライトは保存されません。」). Turning 「共有の端末」 on also deletes the saved highlights; as they are the learner's own work, it first asks in the page with the counts (「この端末に保存したハイライト（3 つのファイル、25 件）も削除します。元に戻せません。」, 削除して切り替える / キャンセル). With none saved it switches at once.
- **Colours** (fixed per background of 文字と背景; the header's swatches use the white ones, since the page cannot see the book's background). The smallest CIE76 ΔE between any two colours under Machado (2009) simulation at full severity, and the text contrast of each colour:

  | Background | Yellow | Pink | Blue | Normal | Protan | Deutan | Tritan | Text contrast |
  |---|---|---|---|---|---|---|---|---|
  | white `#ffffff` | `#fff066` | `#ff9eb0` | `#79b8ff` | 61 | 37 | 54 | 38 | 14.8 / 8.9 / 8.4 |
  | sepia `#f6eedb` | `#f5e04a` | `#f797a8` | `#70aae6` | 59 | 33 | 50 | 33 | 11.7 / 7.4 / 6.4 |
  | black `#000000` | `#7d6800` | `#a5304a` | `#1f4f94` | 64 | 42 | 32 | 44 | 4.6 / 5.7 / 6.8 |

  The weakest pairs are pink–blue (protan) and yellow–pink (tritan). Yellow on white under tritanopia is only ΔE 16 from the page: faint, but the band still reads.
- **How it is kept apart.** The frame side (`play/markup-frame.js`) is part of the trusted prefix, after the shim; it paints, anchors and asks. The page side (`play/markup.mjs`) keeps the record and accepts `{egaViewer: "markup-…"}` requests only from the frame, in exact shapes with bounded sizes, at most 2,000 highlights per file, and always for the `docId` it read from the file itself. **Known limit:** the frame's script runs beside the file's, so file script can read the highlights the page sends in and can recolour or delete them. The record is chosen by the `docId` the file declares, and docIds are not secret (every copy of a file carries its own), so a hostile file that declares another file's docId gets that file's highlights and can change them. It cannot send them anywhere (the frame's `connect-src 'none'`) and cannot reach any record whose docId it does not declare. The meanings a learner gives colours stay in the page: the frame gets the plain colour words only. While the markup bar is open, Esc pressed in the file closes the bar and does not reach the file's player.
- `tools/test-viewer-markup.mjs` (Chromium; `--webkit` for WebKit) checks all of the above, including the Markup button and its hint with the slides alone, no button for a file with no book, and phone width, highlights across emphasis, ruby, inline math and a term link, ruby segments (group ruby widened, mono ruby per character in both forms, an older record rewritten once, one 暗記 band over a word and its reading), a revised file, forged requests, the keyboard in 暗記, Slides and book (nothing over the slides, the arrow keys still move the file) and the phone width.
- **The slides' text** (stage 2, handoff #107): text on a slide is selected and highlighted like the book's, and 暗記 hides it. The anchor is `{slide: the slide's key, quote}` (annotations.md), looked for only in the slide on screen. Highlights are painted in layers fixed over the page (the stage is scaled to the screen, so the boxes are measured where the text is now), again when a step appears, the frame resizes or an animation ends; text of a step not shown yet is not painted. A fixed layer is a stacking context of its own, so the colour layer is blended as a whole with the slide (multiply on a light slide, screen on a dark one), and the 暗記 bands and their buttons are in a second layer above it. The list groups highlights by slide in the file's order, then by section of the book; a highlight on a slide that is no longer in the file is listed under 「場所が見つからないハイライト」.
- **Later:** the Markup button inside the presentation bar itself (a hook in the player, `kit/`), the script pane (台本で読む).

## Notes (per slide and per section of the book)

A learner's own words (handoff #107, textbook-reader memo §3.2B, annotations.md Note record): one note per slide and one per section of the book, typed (on an iPad, Scribble turns Pencil writing into text too).

- **A slide's note**: 「メモ」 (Notes) in the header, or `m` (also pressed in the file: `play/lesson-shim.js` 7), shows the same memo area as handwriting below the slide (the file's frame shrinks to the slide's height; it works in the slides view and closes when the player's view changes to the book). The note's text size is set in stage units (26 for a width of 1280) and scales with the slide, so its lines break at the same words on every screen and handwriting over it (a line under a word, an arrow from a word up into the slide) stays in place. Narrower than 600 px (a phone) that text would be too small: the memo area keeps the page's text size (16 px) and shows no handwriting. While typing, the arrow keys and Space stay in the note (not passed to the file); Esc leaves it (the focus goes to the 「メモ」 button). 「手書き」 lets the pen draw over the memo area, and the note cannot be typed meanwhile; pressed alone it opens the memo area with it and closes it again at the end.
- **A section's note**: with the book (or the slides and the book) on screen, 「メモ」 or `m` opens the note of the section being read (the last one that starts above the upper third of the frame and is still on screen), without going back to the slides (the owner's iPad, 11/27). while the markup bar is open (or when a section has a note), the end of each section of the book has a button 「この節のメモを書く」 (or 「この節のメモを開く」). The button is in the file's frame (a shadow tree), but **the note's text never goes into the frame** (standards' decision 1, 11/25: the file's scripts cannot read what the learner wrote). It opens the note in the page, below the file's frame (the frame gives it room; nothing over the frame), at the page's text size.
- **Quotes**: the small window that appears for selected words (in the book or on a slide, and for a tapped highlight) has 「メモ」. It adds a quote card to the note of their slide or section, and puts the focus on an empty line after it (to explain it in one's own words). **A quote makes no highlight** (the owner 11/27: a quote is not something to hide in 暗記): the quoted words get a dotted underline (purple, unlike the solid red lines a slide may have), which 暗記 does not hide. Words that already have a highlight keep it, and the quote keeps its id (annotations.md: "when one exists"). A quote cannot be edited; it copies the words, so it stays when the file changes and the place is gone. ↗ goes to the place (another slide first, if need be) and the words flash; 「削除」 removes the card and its underline, a highlight stays.
- **Storage**: in the same record as the highlights (IndexedDB `egatari-viewer-notes`, per docId; a file without one is kept under `file:` and its SHA-256), as `notes`. Saved 0.5 s after typing stops, when the focus leaves the note, and when the file closes; there is no Save button. At most 20,000 characters a note and 1,000 notes a file. Nothing is saved on a **shared device** (the memo area's placeholder and the section's note say 「共有の端末なので、メモは保存されません。」); turning 「共有の端末」 on deletes the notes too, after a question that gives their number.
- **List**: after the highlights, 「メモ（n 件）」; each opens its note. Notes whose slide or section is no longer in the file are listed under 「場所が分からないメモ」 and never deleted on their own (they can be, after a question).

## Export and read in

From 「エクスポート」 in the markup bar (handoff #107, annotations.md Exchange file). The files are made in this page and saved by the browser (a download); nothing is sent anywhere.

- **PDF (to print or look back)**: a handout. One A4 portrait page per slide: the slide as it ends (every step shown), smaller, with its memo area below (typed text, quotes, handwriting). The note's text keeps the same size relative to the slide as on screen, so handwriting lands where it was drawn. Slides without a note or handwriting are left out unless 「メモのないスライドも入れる」 is on; notes on sections of the book come after. Slide highlights are not drawn. **Only the page calls print()** (on an iPad, print() in a frame prints the whole page; standards 11/27 withdrew allow-modals): the page draws the notes and handwriting in `#print-root` (shown only in print), never in the file's frame. The slides come from the file loaded again in a frame with `sandbox="allow-scripts"` (the playing frame's policy; `play/print-frame.js` as its prefix), in one of two ways while both are tried: **A**, that one frame shows the slides one A4 page (273 mm) apart and the page lays its memo areas over it; **B**, that frame makes a still copy of each slide (HTML, a canvas as an image), which the page checks (no scripts, frames or outside loads) and shows in frames with `sandbox=""`. The one that prints on an iPad stays.
- **Markdown (for other note apps)**: the slide's title (or section's) as headings, the note's text, quotes as `>` lines, and the words of highlights not quoted. Handwriting is not included (a line says so for that slide). File name 「（題名）のメモ（2026-11-25）.md」 (the device's date).
- **Backup (to move to another device)**: `.ega-notes.json` (annotations.md Exchange file): the docId (empty for a file without one, which is joined by `madeOn.fileSha256`), `madeOn`, highlights, notes and handwriting (`ink: [{slide, strokes}]`). File name 「（題名）のメモのバックアップ（2026-11-25）.ega-notes.json」 (ending in `.json` so that an iPad opens it). A shared device keeps no handwriting, so its backup has none.
- **Read in a backup**: only one for the file that is open (the same docId, or for a file without one the same SHA-256); another file's is refused. The page checks its contents as it checks its own (shapes, sizes, counts); for an id on both sides the later `modified` wins, and a note for a place that already has another note adds the blocks it does not have yet to its end. Handwriting adds no stroke twice. Nothing is deleted; reading the same backup twice adds nothing.
- `tools/test-viewer-notes.mjs` (Chromium; `--webkit` for WebKit) checks the memo area (place, saving, per slide, arrow keys, Esc, with handwriting, opening again), `m`, phone width, a section's note (the button, no text in the frame, the panel below the frame), quotes in the book and on a slide (the highlight reused, ↗, the flash), 暗記 on a slide, the list, the print frame (sandbox, layout), Markdown, and the backup (another file refused, read in on another device, twice, a broken file).

## Handwriting (the slide and a memo area)

- **Handwriting** (in the header, next to Markup) shrinks the file's frame to the slide's height and makes the slide (1280 × 720 coordinates) and a memo area below it one surface. A stroke can run across both, such as an arrow from the memo up to the slide. While it is on, the button reads 「手書きを終了」 (End handwriting) and looks pressed; press it to go back. The header's close button reads 「ファイルを閉じる」 (Close file) so the two are not mistaken for each other (「閉じる」 on a phone, which has no handwriting). Not offered for a file with a Live (the Live pane needs the room) or on a screen narrower than 600 px (a phone: the memo area would be too small, and the header needs the room). The decision: textbook-reader memo §3.2B (no sticky notes; a memo area per slide; no handwriting on the book's text, which reflows and would leave strokes behind).
- **Writing**: Apple Pencil and a mouse write. A finger does not (so the palm can rest on the screen); a finger swipe across the surface moves a step. Without a Pencil, turning on 「指で書く」 (Draw with a finger) lets a finger write. A stroke in progress uses every point of `getCoalescedEvents` and draws the `getPredictedEvents` points faintly ahead (the owner's iPad check of the prototype, 2026-11-18: both available, 6 ms median and 7 ms at the 90th percentile from the move to the paint).
- **Tools** (the bar under the surface; all icons, named for screen readers and as tooltips): pen, eraser (removes each stroke it touches; the Pencil's eraser end too), pen colour, undo, previous and next, draw with a finger. **Pen colours** are a fixed set of three, black, red and blue; no free colours (§3.2A). A stroke keeps the colour's name and is painted in the shade that reads on the slide's background (light: #1f1f1f, #d22a3a, #1f5fbf; dark: #f2f2f2, #ff7b88, #7db8ff).
- **The memo area's background** is the slide's, set off by a small gap and an outline. A light file gets a white memo area even when the Viewer itself is dark. The page cannot look into the file, so the shim inside the file's frame answers the page's request (`{egaViewer: "ink-bg"}`) on every slide with the background colour (`{egaViewer: "ink-bg", rgb: [r, g, b]}`, `play/lesson-shim.js` 5); the page takes only that shape with three whole numbers 0–255.
- **Storage**: this device only (IndexedDB `egatari-viewer-ink`, one entry per file docId, or the file's SHA-256 when it has none, and slide key). Never put in the file, never sent anywhere (writing it into the file is decided after v0.7.0). A slide with seven strokes is about 15 KB (the owner's iPad). Nothing is saved on a **shared device**; turning 「共有の端末」 on deletes the saved handwriting after asking, with the count (「この端末に保存した手書き（2 枚のスライド）も削除します。元に戻せません。」, together with the highlights if there are any).
- `tools/test-viewer-ink.mjs` (Chromium and WebKit) checks the frame's height, the tools' names (Japanese and English), the memo background on a light and a dark file, the three colours, the eraser and undo, leaving a slide and coming back, opening the file again, a finger (no stroke, a swipe, draw with a finger), that a malformed `ink-bg` is ignored, and the shared device.

## How the file is kept apart

An Egatari file is untrusted HTML with scripts (spec §11). The page plays it as a host would (spec §10.1):

- The file runs in an `<iframe sandbox="allow-scripts">` whose document is `srcdoc`: no `allow-same-origin`, `allow-popups`, `allow-forms`, `allow-modals`, `allow-downloads` or `allow-top-navigation`. Its origin is opaque, so it cannot read this page's OPFS, IndexedDB, localStorage or cookies, or reach its DOM. It cannot open windows or navigate the page.
- The document is the page's **trusted prefix** followed by the file's bytes unchanged (`app/preview-doc.js`, the same as Studio's preview). The prefix carries the preview policy (`connect-src 'none'`, `frame-src 'none'`, only `data:` and `blob:` resources), so it is in force before any byte of the file is parsed. The page never searches the file's markup for a place to insert anything. The prefix also holds the page's small shim (`play/lesson-shim.js`): it sets `?embed=1` (spec §9.4) and hands links that leave the file to the page.
- A `srcdoc` document also inherits the page's own policy; both apply. That is why the page's policy allows inline scripts and styles (files need them) while the page itself uses none: its own scripts are files, and everything it shows from a file or a service (titles, file names, Live text, link addresses) is set as text, never as markup. The policy is otherwise as tight as it gets, and `tools/test-play.mjs` checks it exactly: `default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; media-src data: blob:; connect-src 'self' https://live.egatari.org wss://live.egatari.org; worker-src 'self'; manifest-src 'self'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` (`connect-src 'self'` is for the service worker's install; `form-action 'none'` because an Android share is a POST from the system, not a form in the page). **A follow-up idea:** serve the file frame from its own path (e.g. `/frame`) with a header CSP and fill it by message instead of `srcdoc`; the page would then no longer inherit into the file and could drop `'unsafe-inline'`. The page's `connect-src` lists its Live endpoints, and the file's prefix narrows that to `'none'`, so only the page can reach a Live room.
- **The file's own CSP `<meta>`** (written into play-only files that carry a Live room, live §2.4; from format 1.0 on, into every file, format spec §4.2) lands inside the file's `<head>` after the prefix and is enforced as well: the browser applies every policy, so the file gets the narrowest of the three. Its `connect-src` (the Live endpoint) has no effect inside the frame. **The `deck-extensions` block** is data: the page reads it itself with a parser that runs nothing (`play/scan.mjs`, parse5 under limits), and the file's own Live client (`kit/live.js`) sees that it is framed and does not connect (live §2.1). Because the page shows Live in its own chrome, it hides the file's Live mark and pane with a rule in the prefix (they could only say "you cannot join from here").  `tools/test-play.mjs` plays a copy of a fixture that carries the §4.2 baseline (`connect-src 'none'` and the `liveCsp` shape) and checks that a fetch from the file is reported against both the file's policy and the prefix's.
- Messages from the frame are untrusted requests: the page accepts them only from that frame (`event.source`), only with an opaque origin (`"null"`), and only in these shapes: a position event (spec §9.4 `position`, or the player's older `deck-pos`), the markup requests `{egaViewer: "markup-…"}` (see [Markup](#markup-highlights-and-recall)), and the link request `{egatari: "openLink", href, text, download?}` (spec §9.4: exactly those members, `text` at most 200 characters, `download` only as `true`, sent for a link with a `download` attribute). Anything else is ignored. The shim sends `openLink` only on the viewer's own activation (a trusted click while the frame has a transient activation); clicks made by file script send nothing. Lesson code can still post the message itself, so the page treats it as untrusted: it applies §11 and never opens anything without a tap in its own box. (Studio's editor preview has no such message: there the player shows the destination without a way to open it, §11 (g).)
- **Fullscreen.** The frame has no fullscreen permission (no `fullscreen` in its `allow`, and the page's `Permissions-Policy` says `fullscreen=(self)`): a file cannot take the screen by itself. The player's 「全画面」 (Fullscreen) button and `f` still work: the shim replaces the file document's fullscreen API (`requestFullscreen`, `exitFullscreen`, `fullscreenElement`, `fullscreenEnabled`, the `webkit` names and the `fullscreenchange` events) with one that asks the page `{egaViewer: "fullscreen", on}`; the page puts the frame element itself into fullscreen (`requestFullscreen`, or `webkitRequestFullscreen` on older iPadOS) and reports `{egaViewer: "fullscreen-state", on, enabled, refused?}`, also when the viewer leaves with Esc or the system's gesture. So any player inside the file, an older one too, enters, leaves and shows its button right. The browser enters fullscreen only on the viewer's own activation (the tap in the frame reaches the page), so a file's script alone cannot; the page accepts the request only from the frame and only in that exact shape. Why not `allow="fullscreen"`: Safari (the engine on iPad) ignores it on an opaque-origin `srcdoc` frame (it would need `allow="fullscreen *"`), and it would give the file a fullscreen of its own beside the page's. Where the browser has no element fullscreen (iPhone Safari), the player has no fullscreen button and the key list leaves `f` out; the start screen's add-to-Home-Screen line already says how to get the most screen there. `tools/test-fullscreen.mjs` checks all of this in Chromium and WebKit.

## Links

Links the file asks the page to open go through the player's own rule, `kit/core/link-policy.mjs` (spec §11). The box is in the page, outside the frame, so the file cannot draw over it. It shows the destination's host and address; it refuses every scheme but `https:`, `http:`, `mailto:` and `tel:`; it confirms every time when the text names another host, the destination is not plain `https:`, the link downloads, the address has a user name or password, or the host is punycode. A file next to this one (a relative link) cannot be reached from this page and is refused with that reason. A link that would save a file (`download: true`) is refused too: the box shows its host and 「このファイルからは、ほかのファイルを保存できません」 (Files can't be saved from this file), and nothing opens. Opening is an ordinary link with `noopener noreferrer` that the viewer taps. A plain `https:` host agreed to once is remembered in memory for the session (§11 (f)); the next link to it shows a plain box with the host name and 「開く」 (Open), without the warning. One tap is still needed: the page never opens a link on a message alone, and Safari does not let a page open a tab without a tap in that page. One box shows at a time, and for 1.5 s after it closes new requests are ignored, so a file cannot keep the box up.

## Live

When a file carries a valid `extensions.live` with a key (a play-only file exported "with a live room"), the page acts for the file (live §2A): it shows the 「ライブ」 button and pane in its own chrome and holds the WebSocket itself.

- **Join first.** A file with Live opens on a start screen: 「参加する」 (Join) with the window and the destination host, and 「参加しないで見る」 (Watch without joining). The file's frame is placed only after one of them, so the Join tap can never meet the frame. Watching without joining makes no request at all; Join stays available in the Live controls. For an endpoint the page does not connect to, the start screen offers the room's join page link instead of Join.
- No request before the viewer presses Join, and none outside the window. Only what an activity needs is sent: questions, votes, a name if the viewer types one, a random id made on this device, and pings. Text from the room is shown as text. Retries follow `LivePolicy.plan` (`kit/core/live-policy.mjs`).
- The page learns the current step from the file's position events, to show that step's poll; a step with a poll is announced.
- **Layout** (`play/layout.mjs`), chosen once when the file starts, from its activities and the screen, and kept while it plays (only a rotation, or a desktop window resize, lays it out again). The screen is the visible size (`visualViewport`), and the page itself is made that tall while a file plays (`--view-h`), not `100dvh`: in Chrome on iPad, `100dvh` stayed at the portrait height after a rotation to landscape, so the frame ran below the screen, with a dark band above the slide and a page that scrolled back to the top (2026-11-19):

  | Lesson | Phone portrait | Phone landscape | Wide screen |
  |---|---|---|---|
  | No Live | the file fills the page | same | same |
  | Live without polls | a 44 px bar below the file: indicator, 「退出する」 (Leave) or Join | the side slack (below) | the 44 px bar |
  | Live with polls | the pane below the 16:9 stage (the poll first) | the side slack (below) | the 340 px side pane |

  In phone landscape (height up to 500 px) the page's bar is hidden and the stage fills the height. With at least 120 px of side slack (19.5:9 phones: about 150 px) the controls take a column there: close, indicator, Leave or Join, and 「投票」 (Poll), which shows the poll in the column. Without slack (16:9 phones) the variant is one constant, `NO_SLACK_VARIANT` in `play/main.js`. **'overlay'** (the default, the owner's choice) keeps the full screen for the slide and lays a 28 px indicator over the frame's top edge, shown from the moment the frame is placed; the poll opens as a sheet over the frame. **'strip'** (the alternative) shrinks the stage by 28 px and gives the controls a strip above it; the poll replaces the strip's content as one row. `?noslack=strip` or `?noslack=overlay` switches it for measuring.
- **Why the layout is fixed.** In one line: lost taps come from page chrome that switches from hidden to shown over the out-of-process frame. The file's frame runs in its own process, and Chrome hands a tap to it by hit-test data from the last frame shown. A control that had just appeared where the file was (a pane shown over the frame, or a frame that just shrank) lost its first tap to the file in 12 of 45 fast taps under load. With Join before the frame, and controls placed before the frame and never moved, `tools/play-tap-measure.mjs` (3 copies at once, 15 sessions each, taps as soon as a control is visible) counted no lost tap: Join 0/45, the poll in portrait 0/90, in landscape with slack 0/135, without slack 0/225 for both the strip and the overlay variant, the first tap after a rotation 0/45, Leave 0/45. The overlay is safe only because its indicator is always shown over the frame and never toggled over it (see the comment at `NO_SLACK_VARIANT`); any change to that must be measured again. The slide is 375 × 211 px in portrait (375 × 667), 693 × 390 in landscape at 844 × 390, 617 × 347 (strip) or 667 × 375 (overlay) at 667 × 375, and 940 × 529 at 1280 × 800 with the side pane.
- **Touch targets.** Each poll choice's whole row is the target: 44 px tall in the panes, the slack column and the overlay's sheet, and at least 24 × 24 px (WCAG 2.2) in the 28 px strip; the same for 戻る, 投票する, 退出する, 投票 and ×. At those sizes the poll fits in the slack column (choices wrap) and in the strip (one row), so no other layer is needed. Measured again with the row as the target and the overlay as the default: the overlay 0/225, the strip 0/225, the slack column 0/135.
- The 「ライブ」 button (portrait and wide screens) moves the focus into the Live controls; Escape returns it.
- **Keys.** The navigation keys (← → ↑ ↓, Space, PageUp/PageDown, Home/End) move the file wherever the focus is. The page focuses the frame when the file has loaded (Chrome loses the focus given to the frame's first, empty document; Safari may refuse it), and a navigation key pressed while the focus is in the page (its bar, a button, the Live pane) is handed to the file as `{egaViewer: "key", key, shift}`; the page's file shim presses it the way the player's own buttons do (a keydown on the file's document), so it works with any player inside the file. Not handed over: keys in a field or a widget that uses the arrows, keys while the link box is open, and Space on a button or link (it presses it). Measured by `tools/viewer-keys-check.mjs` in Chromium (`test-play`) and WebKit (`test-viewer-webkit`, Desktop Safari).
- **Offline.** Join on a device with no network (`navigator.onLine` false) does not retry: it says at once 「この端末はネットワークに接続していません。Wi-Fi などに接続してから、「もう一度試す」を押してください。参加しなくてもファイルは見られます」, and 「もう一度試す」 joins once the device is online. Every message that reports a failure ends with what to do next.
- The page connects only to endpoints that its own policy allows (the build's `--live-endpoint`, by default `https://live.egatari.org`). For any other endpoint it shows the room's join page link (`/join#room=…&key=…`, the key after `#`), which opens in a new tab.
- **Nothing from Live is relayed into the file.** v1 relays one thing out of it, the step on screen. Not yet: drawing a region on the slide for a question (the file's frame has no way to hand strokes to the page yet).
- The teacher's own editable file has `extensions.live` without a key: it plays, without Live.

## Service worker, offline and versions

The service worker (`play/sw.js`) caches only the page's own files, listed by the build, under a cache named by the version (the package version and a hash of the files): the app shell, which is the page, its script, the reader Worker, the style sheet, `guard.js`, the manifest and the icons (the page uses the system fonts and loads no font file). It never stores anything else: not a file, not a shared file. Once the Viewer has been opened, it opens with no network, from the Home Screen as well; files are read on the device and never uploaded anywhere, online or not.

**Updates apply on the next launch.** A new version installs beside the running one and waits; there is no update button. It takes over only when the Viewer is launched: when no window of it is open the browser activates it by itself, and a page freshly launched at its start screen (no file open) asks the waiting worker to take over and reloads once. The worker agrees only when that page is the Viewer's only window (`activate-if-idle`), so a file playing in another window is never swapped; while it launches, a page that was told `busy` asks again each second (the window it replaced can still be listed for a moment while it unloads, or another window may close). An update found more than 10 s after a launch, or while a file plays, waits for the next launch; returning to the Viewer at its start screen counts as a launch. Nothing is requested while a file plays (the page checks for updates only at a launch).

`tools/test-play.mjs` checks: the cache holds exactly the app shell; offline, a navigation and a reload open the Viewer with its logo, manifest and icons, and a file plays, with no request reaching the server; a version found while a file plays waits (same version, same slide, no reload), also when a second window is launched; after every window is closed the next launch runs the new version and only its cache remains; a launch at the start screen takes over, also once another window (playing a file) closes during the launch; no file bytes appear in any request or WebSocket frame, with or without Live.

## Touch

The file's own player (`kit/tools.js`) takes touch itself, so the page adds nothing for it: a tap on the slide wakes the toolbar (前へ, 次へ, 字幕, 読み上げで聞く …), a tap that wakes it does not press a button under it (`REVEAL_GUARD`, 350 ms), the bar is shown for 5 seconds when the file opens, and a small handle brings it back when it is hidden. A swipe across the slide, or a tap on its left or right edge, goes back or on one step ([reference](reference.md), handoff #97); in handwriting the page's surface lies over the file, and its own finger swipe does the same. The file shim (`play/lesson-shim.js`) only sets the embedding mode and hands links out of the file to the page. `tools/test-viewer-webkit.mjs` checks the bar, captions and read-aloud in Playwright's WebKit with iPad sizes.

## Accessibility

The aim is WCAG 2.2 AA for the Viewer's own page (the header, the start screen, the markup bar and list, the memo area and a section's note, the export dialog, the handwriting tools, the dialogs, the Live join screen and pane). `tools/test-viewer-a11y.mjs` (Chromium; `--webkit` for WebKit; `--report` lists each finding, `--json <file>` writes them) runs axe-core with the WCAG 2.0/2.1/2.2 A and AA rules on the page in these states: the start screen (Japanese, English, dark), a file open as slides and as a book (light and dark), the markup bar, the markup list with a highlight, the confirmation for deleting a colour, the link box, a file with a Live before joining and while watching, and a file with edits: the credit line under the title and its list (light and dark), handwriting: the surface and its tools (light and dark), and notes: a slide's memo area, a section's note and the export dialog (light and dark). It fails on any violation in the page. The file's frame (the player inside the file, `kit/`) is checked in the same states and listed, but does not fail the test. axe finds only part of WCAG; the keyboard, screen-reader (VoiceOver, NVDA) and 400% zoom checks are done by hand.

## Building

```sh
node tools/build-play.mjs [--out _play] [--live-endpoint https://live.example.org …]
```

writes `_play/` (not committed): `index.html`, `guard.js`, `play.css`, `play.js` (bundled with esbuild from `play/main.js`, importing `kit/core/link-policy.mjs`, `kit/core/live-policy.mjs`, `kit/core/bounded-html.mjs` and `app/preview-doc.js`: the player is not forked), `reader.js` (the Worker that scans a file), `sw.js`, `manifest.webmanifest` (icons 192 and 512 px from `assets/logo`, and `share_target`), `icons/` and `_headers`. `--live-endpoint` (repeatable) replaces the default list of rooms the page may connect to; the same list goes into the page's `connect-src`.

Test: `node tools/test-play.mjs <work dir>` (part of `npm test`). It builds into the work dir and serves it with a small server that applies `_headers` the way Cloudflare does, and uses `tools/live-fake-server.mjs` as the Live room.

To try it locally: `node tools/build-play.mjs && npx wrangler@4.124.0 dev -c play/wrangler.toml` (wrangler is not a dependency of this repository; `npx` fetches that version, the one egatari/live pins).

## Hosting: Cloudflare Workers static assets

The page is static files with response headers. It is hosted as **Cloudflare Workers static assets** (`play/wrangler.toml`, `play/wrangler.production.toml`, `play/worker.js`), not Pages:

- Workers is where Cloudflare is putting new static sites, and the Live service (egatari/live) is already a Worker: one tool (wrangler), one way to configure and deploy, and the same split between a development config and a production config.
- Static assets read `_headers`, which carries the policy and the frame refusal for every file, so the files are served without running code. The page itself (`/`) is also `Cache-Control: public, max-age=0, must-revalidate, no-transform`: Cloudflare then never rewrites it, so its Web Analytics cannot inject a beacon script (its documented behaviour; the policy would block the script anyway, but the page must not carry one). Only the HTML: `no-transform` also stops the edge's compression, which the scripts keep.
- A small Worker answers only what matches no file: an Android share (`POST /share`) that arrives before the service worker is installed. It cannot receive the file (nothing is uploaded) and sends the page a 303 to `/?share=nosw`, which asks the viewer to open the app once and share again.
- A custom domain (`routes = [{ pattern = "viewer.egatari.org", custom_domain = true }]`) makes `wrangler deploy` create the DNS record and certificate itself.

The page refuses to run in a frame: `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY` on every file, and `guard.js` checks `window.top` before anything else runs (defense in depth).

## Deploying (for the maintainer)

Not done yet. Every deploy needs the owner's approval.

1. `npm ci && npm test` on the commit to deploy (or at least `node tools/test-play.mjs`).
2. `node tools/build-play.mjs` (production: no `--dev-loopback`; the default Live endpoint `https://live.egatari.org`).
3. Sign in if needed: `npx wrangler@4.124.0 login`. The `egatari.org` zone must be in the same Cloudflare account.
4. `CLOUDFLARE_ACCOUNT_ID=<account id> npx wrangler@4.124.0 deploy -c play/wrangler.production.toml`. This creates (or updates) the Worker `egatari-viewer`; with `custom_domain = true` it also creates the DNS record and certificate for `viewer.egatari.org`. The account id is passed at deploy time, never committed.
5. Check: `curl -sI https://viewer.egatari.org/` shows the `Content-Security-Policy` with `frame-ancestors 'none'` and `X-Frame-Options: DENY`; open the page, open a file, and install it on a phone.

## Self-hosting

You may serve the same files from your own origin. Requirements:

- **A host that can send response headers.** Send the headers in `_headers` for every file: the `Content-Security-Policy` (with `frame-ancestors 'none'`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and the others listed there. Cloudflare (Workers or Pages) and Netlify read `_headers` as it is; with nginx, Caddy or Apache, copy the lines into the server's configuration. Do not use GitHub Pages or any host that cannot send headers: such a host cannot refuse to be framed, and the page's policy then comes only from the browser's defaults.
- **HTTPS** (a service worker and OPFS need a secure context).
- **Its own origin**, separate from any editor (live §2A.4): not the origin of an Egatari Studio you also host, so that files played there can never reach the editor's storage.
- **`POST /share`** answered with `303 See Other` to `/?share=nosw` (what `play/worker.js` does), or the share target only works after the app has been opened once.
- **Live rooms**: build with `--live-endpoint <your room service>` for each room service the page may connect to; files with other endpoints get the join link only.

## Site player

A static site that cannot send headers (egatari.org on GitHub Pages) plays its samples with the site player, not the Viewer: `node tools/build-site-player.mjs [--out dir]` writes `site-play.js` (one ES module built from `play/site-player.mjs`: the Viewer's frame, trusted prefix, file shim and link box), `site-play.css` and `BUILD.json` (Studio version and commit, the SHA-256 of each file, and the page policy). The site vendors these files pinned to a Studio commit.

- The page is `<div id="egatari-player" data-lock="<lock URL>" data-files="<folder URL>">` and `<script type="module" src="site-play.js">`, opened as `?id=<id>`; an element with `data-player-title` gets the file's title. Its first `<meta http-equiv="Content-Security-Policy">` is `BUILD.json`'s `pageCsp`: the Viewer's policy without Live (`connect-src 'self'` for the lock and the file) and without `frame-ancestors`, which a meta cannot carry. The player refuses to run inside another page's frame instead (it plays nothing there).
- The lock is JSON `{lessons: [{id, sha256, size, title, lang}]}` (other keys are the site's own; egatari.org writes it from a samples release and its SHA256SUMS). The file is `<data-files><id>.ega.bin`, served from the same origin as `application/octet-stream`, so opening it directly downloads it and never renders it on the site's origin (spec §10.1). The bytes must match the lock's size and SHA-256 before anything is parsed; otherwise nothing plays and the page says why. The hash catches a stale or damaged file, not a compromised host (lock and file come from the same origin).
- The file plays as in the Viewer: `srcdoc` = the trusted prefix (the preview policy, then the file shim) + the bytes unchanged, `sandbox="allow-scripts"` (an opaque origin). The `srcdoc` document inherits the page's meta policy too. The page takes only openLink (through the link box, §11) and fullscreen requests from the frame. No Live, no markup, no recent files, nothing stored, no service worker.
- `tools/test-site-player.mjs` (Chromium; `--webkit`) serves the page with no headers, as such a host does, and checks: the file plays in an opaque origin with no storage, page or network access; a changed byte, a longer file, an unknown id or no id plays nothing; link requests go through the link box and a `javascript:` link is refused; requests not from the frame are ignored; inside another site's frame nothing plays.
