# Editor app (no install)

English | [日本語](editor.ja.md)

A web page that opens a working folder directly and does what the [dev server](dev-server.md) does: preview, edit the source and the script on the slide, and leave comments. It also opens an [Egatari file (`.ega.html`)](reference.md#single-file---portable) (one HTML file that carries its source, following the [Egatari format](https://github.com/egatari/egatari-spec)) without any folder, edits it in memory and saves it again. There is nothing to install and no terminal to use. The first screen puts Egatari files first (“Open a file (.ega.html)…”, “New…”; working folders through “Work in a folder…”).

| Form | What it is | Here |
|---|---|---|
| Working folder | A folder with `deck.html`, `narration.md`, `audio/` …; the commands, AI coding tools (Claude Code, Codex, Gemini CLI …) and other editors read and write it | Edit it with “Work in a folder…” (Chrome / Edge) |
| Egatari file (`.ega.html`) | One HTML file that carries its source and audio (`--portable`); open it in a browser to play | Edit it with “Open…” (any browser) |
| Play-only (`--play-only`) | An Egatari file without the source | Cannot be edited (open the original Egatari file or the working folder) |
| Built HTML (`out/deck.html`) | The presentation output of the command line (`node kit/build.mjs`; the editor no longer exports it) | Cannot be edited (open the working folder) |

- **Browsers:** Google Chrome or Microsoft Edge on a computer (Windows, macOS, Linux, ChromeOS). Folders use the File System Access API (`showDirectoryPicker`), which Safari and Firefox do not have; on other browsers the first screen says so, together with the way to make a new lesson there: **New… → Have a chat AI write it**. An Egatari file can be opened and edited in any current browser; without the file pickers, saving downloads the file, and each save makes a new file in the downloads (the first screen and the save notice say so: open the newest one next time).
- **Network:** none, apart from loading the editor itself. The working folder or file is read and written in the browser and is never uploaded. Only if you use **Make AI voice on this computer** (in the [Audio panel](#script-audio-audio-panel)), a separate TTS window of the editor's site downloads the model; the editor page itself still connects nowhere.

## Getting the editor

| Form | How | Notes |
|---|---|---|
| Hosted | <https://studio.egatari.org/> | Published from `main` by `.github/workflows/pages.yml`. Loads only the font files a lesson needs. The old address `…/editor/` redirects there |
| Single-file editor (`editor.html`) | `npm run build:app`, then double-click `dist/editor.html` | About 10 MB: all font files are inside. Works from `file://` in Chrome and Edge; you can copy the file to anyone |
| Your own server | `npm run build:app`, then serve `dist/` as static files | Any static host (https, or `http://localhost`), at the root or under a path |

`npm run build:app` (`node tools/build-app.mjs [--out dist] [--no-single]`) needs `npm ci` first (it uses esbuild, a pinned dev dependency).

## Using it

1. **Open a lesson.** An Egatari file opens with “Open a file (.ega.html)…” on the first screen or **File ▾ → Open…** ([below](#egatari-files-no-folder)). For a working folder (the folder with `deck.html`; if there is no `deck.html`, the first `.html` file at the top of the folder), drop it onto the page or press “Work in a folder…” (first screen, or **File ▾**). The browser asks once whether the page may edit that folder.
   - **The first screen**, top to bottom: **New…** (the main button: a chat AI writes the lesson, see [below](#drafting-with-a-chat-ai-paste-and-fix-requests)), the drop area (“Drop a .ega.html here”) with **Open a file (.ega.html)…**, **Recent files**, **Samples**, a small link **Make it with Claude Code or Cowork (advanced)** (its target is one constant, `WITH_CLAUDE_URL` in `app/main.js`, until the page is decided) and **Work in a folder…**. The table of the four kinds of files is in the help (**?**). A new working folder is made with `npm run new`.
   - **Recent files**: working folders and Egatari files are listed on the first screen (the browser keeps the handles in IndexedDB; the contents are not stored). When you reopen one, the browser asks for permission again (for an Egatari file only to read; Save asks to write). An Egatari file is listed only when the browser gave a file handle (Open a file (.ega.html)… or drag and drop in Chrome / Edge), not in Safari or Firefox.
   - **Samples** (hosted editor only): the first screen lists the samples of this repository as Egatari files (`examples/minimal`, `pitch-fictional`, `kokugo-kanbun`, `tmlr2026-calibration`, without audio). **Open** fetches the file from the same site (`examples/<name>.ega.html`) and opens it exactly like a file you chose: the same import checks, the code question for `tmlr2026-calibration` (it has its own parts) and the editing prompt before the first edit. The the Offline editor (`editor.html` from `file://`) does not show the list.
2. **Edit.** The keys are the same as the dev server (and the toolbar has buttons for them; until the right-panel tabs arrive they are a temporary group **Edit (e)**, **Script (n)**, **Comments (c)**, **Audio**):

   | Key | Action |
   |---|---|
   | `e` | edit mode; **double-click** an outlined element to open its source (HTML, with math as `\( … \)`), ⌘/Ctrl+Enter to save |
   | `l` | show later steps faintly (on/off, an option like captions): every step is shown, steps not yet reached are dimmed (`--preview-opacity`, 0.45 by default); the current step carries no mark; answers marked `data-preview="none"` stay hidden. The same as `?mode=talk&preview=1` |
   | `n` | script drawer for the step on screen (speaker, add / delete / reorder turns) |
   | Alt+click (Mac: ⌥ Option+click) | leave a comment about that element (`comments.json`); the point you clicked is kept as a pin |
   | `m` (or the “Marker (m)” button in the edit-mode bar, or the pen button of the slide controls, which reads “Marker”, with the key `m`, while editing; `d` also opens it) | marker, in edit mode only: draw a circle or an arrow on the slide; when you let go the comment box opens for that mark in the side panel. While it is open you can keep drawing (an arrow plus a circle, several marks, up to 20): each stroke joins the same comment. Leave keeps all the marks with the comment (`strokes`); Cancel discards them all |
   | `c` | list of open comments, numbered; while it is open, the pins of the step on screen are marked on the slide. Click one to go to its slide and step (its pin flashes), “Resolve” to mark it done |

   The edit-mode bar, the source box, the script drawer, the comment box and the comment list sit in one side panel on the right (the preview shrinks beside it), under an orange bar **編集中 — アプリ** / **Editing — app**. They are part of the editor page, not of the lesson; **anything inside the slide area can be drawn by the lesson, so trust only controls in the editor's own panels.** While the source or comment box is open, the preview does not take clicks. The preview only points at what you double-clicked or Alt+clicked, and the editor reads the source, shows it and writes it when you press Save (or ⌘/Ctrl+Enter). The keys work with the focus on the preview or on the editor.

   **Edit mode and the presenting tools do not mix.** Entering edit mode turns off the laser pointer, pen and fading pen (ink already drawn stays visible but cannot be drawn on), stops autoplay and its audio, and closes the slide overview, black screen, the key list (?), fullscreen and a half-typed slide number. Lecture and captions stay as they are. While editing, the tool buttons (autoplay, laser pointer, fading pen, colors, clear, overview, fullscreen) are hidden from the toolbar and their keys (`x` `v` Shift+`d` Backspace `o` `a` `b` `f`) do nothing; the pen button stays, relabelled **マーカー** / **Marker** with the same icon, and it and the pen key `d` toggle the marker instead of the pen (see the table above); a tool chosen in the presenter view is turned off again. Leaving edit mode brings none of them back. Keys typed into a text field (the source box, or an input inside the lesson) are always text, never tool or slide keys. The current mode is shown at the right end of the status bar (**Editing**, **Presenter tool: Pen**, or **Viewing**) and announced to screen readers; it never covers the slide.

   As with the dev server, a save is refused if the file changed since the preview was built (the source hash or the script revision does not match); reload and try again.

   **Esc** closes the open cards one at a time, topmost first: the source or comment box being written, then whichever of the Audio panel, the [recording mode](#recording-mode-keyboard-only), the script drawer, the comment list and the side panel (quality check, file info, help) was opened last. **Shift+Esc** closes them all. A script drawer with unsaved input asks first. Dialogs and menus close with Esc as before.

   **Where it is saved.** The left end of the status bar always says where the lesson lives (its tooltip explains it). A working folder shows “Saved in working folder “…””: **File ▾ → Save** is shown but does nothing there (it says why), because the Save of each card and recording, importing or TTS write to the folder right away; to make an Egatari file, use **File ▾ → Save as…** (editable, `.ega.html`). An Egatari file shows “Saved to “…”” (Save overwrites it), ““…” is open (Save downloads a copy)” when the browser cannot overwrite it (each Save downloads a new file), **Unsaved changes** when something is only in memory (closing the tab loses it, recordings included) or **Not saved to a file yet** for a lesson that exists only in memory (pasted from an AI chat, or a slides file opened alone).
3. **Work with an AI coding tool.** Keep the editor open while an AI coding tool (or any editor) changes the folder. The editor looks at the files about every 1.5 s; when one changes it rebuilds and reloads the preview on the same slide and step. What you are typing in an editor card or the script drawer stays while the preview reloads (it is in the editor page); if the same element or step changed meanwhile, the save is refused. If the build fails, the error is shown over the preview until the file is fixed.
4. **The toolbar.** It has four items, **File ▾**, **Slide ▾**, **Quality check** and **Preview ▾** (plus the temporary panel group and **?** for help), and fits one row from 1280 px wide (below that it wraps). The menus follow the ARIA menu-button pattern: Enter, Space or ↓ on the button opens the menu at its first item, ↑ at its last; in the menu ↑ ↓ move (wrapping), Home / End jump, a letter moves to the next item starting with it, → or Enter opens **Export ▸**, ← or Esc closes it, Esc closes the menu and returns focus to its button, and Tab or a click outside closes it. While a menu or a dialog is open, keys are not sent to the preview (and `e`, `n`, `c` do not toggle the panels).

   | Menu | Items |
   |---|---|
   | **File ▾** | **New…** · **Open…** · **Save** (Egatari file; in a working folder it explains that the folder is saved as you edit) · **Save as…** (Egatari file: another file, optionally as a new lesson; working folder: an Egatari file, editable) · **Export ▸** (**For participants (play-only)…**, **Print / PDF**, and for an Egatari file **Export working folder…**) · **File info…** · **Work in a folder…** |
   | **Slide ▾** | **Insert slide…** (from a template, or have a chat AI write it) · **Duplicate** · **Delete** (the slide selected in the slide list, or the slide on screen when the list is closed) · **Revise…** · **Change theme…** |
   | **Quality check** | runs the browser quality checker; it runs by itself about 1 s after each build and preview load (not while a build is pending), and its badge shows the errors and warnings it found (in the error colour when there are errors); build and save warnings are listed at the top of the panel |
   | **Preview ▾** | the display modes, one at a time: **Check as a slide show (f)** (also full screen), **Check as a video** (they reload the preview in that mode) · **Show later steps faintly (l)** (on/off for the slide show) · **Check in presenter view (p)** · the note “To present, open the saved .ega.html in a browser” |

   A dot (●) after **File ▾** means an Egatari file has unsaved changes.
   - **Quality check:** the browser quality checker, a subset of `npm run check` that runs in the preview (overflow, font size, title / conclusion length, missing script, palette contrast). The layout part (overflow and the vertical-layout limits, text cut off by a box or going off the slide, font size in figures, title and conclusion length) is the same code as the command (`kit/core/layout-scan.mjs`). Click a result to go to the slide. It is a hint, not the full quality check: there are no part determinism, timeline, morph or accessibility checks, and the numbers can differ slightly from the command quality checker because the window differs.
   - The built HTML (`out/deck.html`) is no longer exported from the editor; build it with `node kit/build.mjs` on the command line.
   - **File ▾ → Save as…** (working folder): writes the lesson with its source and audio as one Egatari file (editable, `.ega.html`) to give to others; the working folder stays as it is.
   - **File ▾ → Export ▸ → For participants (play-only)…:** an Egatari file without the source (format §3.7, the same as `--play-only`): it plays in any browser and cannot be edited. For an Egatari file it is made from the saved file (Save first if there are unsaved changes); for a working folder from the folder. The dialog has a checkbox **Add Live (questions and polls)**; the file name is the lesson title with `.play.ega.html`.
   - **Add Live (questions and polls)** in that dialog: ticking it shows the Live settings in the same dialog, and **Export…** writes the Egatari file (play-only) with Live (questions and polls in class, format extension `live`, draft): make the Live ID and join code in the dialog and copy one string that the host pastes once on the host page (the earlier way, pasting the settings copied on the host page, stays under a fold), choose whether participants can send questions and add polls per step (each shown by a label such as “Slide 4 'XML の壁', step 1”, with the step key in the tooltip), copy the poll settings (with the labels) for the host page, and export. **To fix before exporting** lists what is missing in the editor's language; **Export…** keeps the dialog open and names the first problem until it is fixed. The file name gets a mark on the title side with the day the Live starts, for example `Title (live 10-30).play.ega.html` (`題名（ライブ 10-30）.play.ega.html` in Japanese); the extension stays. Importing the results after the lesson is in **File ▾ → File info…** (attachments). The editor itself connects nowhere; the lesson keeps the settings without the join code. See [Live](distributing.md#live-questions-and-polls-in-class-draft).
   - **File ▾ → Export ▸ → Print / PDF:** the browser's print dialog for the slides (one page per slide with the final state of each, as with `tools/pdf.mjs`; choose “Save as PDF”; slide backgrounds, including the section dividers, print in their screen colors even with “Background graphics” off).
   - **Preview ▾ → Check in presenter view** (or `p` in the lesson): a window with the current slide, the next step, the script as speaker notes, a timer and the drawing tools. It controls the preview in the editor window, which also plays the audio: autoplay started in the presenter view (<kbd>a</kbd> or its button) plays the script audio once, in the editor window. `p` in the preview again closes it. In the presenter view, Esc (when no drawing tool is on), `p` or **Close presenter view (p)** close the window and return focus to the editor; if the presenter window is fullscreen, they only leave fullscreen. While the window does not have focus, a large “Click here to control” overlay takes the first click. Recommended order on a projector: open the presenter view first, then make the audience window (the editor's **Full screen**) fullscreen on the projector.
   - **Stuck in the presenter view?** If it covers the screen and its keys do not respond, on a Mac press cmd+Tab to get back to the editor window and press `p` (on Windows, Alt+Tab; not yet verified on Windows). The key list (<kbd>?</kbd>) shows the same tip.
   - **Black screen in the presenter view:** while the main window is black, the presenter view shows "Black screen", and `b` there also toggles the black screen on the main window. While it is black, the arrows, Space or PageUp/PageDown in the presenter view end the black screen without moving the slide.
   - **Preview ▾ → Check as a slide show** (or `f`): the preview fills the screen, to check it as projected. **Check as a video** shows the preview in the other display mode (Video). **Show later steps faintly** (or `l`) turns faint later steps on or off in the slide show, an option like captions. This is a preview: to present, open the saved `.ega.html` in a browser.
   - **Keys:** after you click the toolbar, header or status bar, the arrows, PageUp/PageDown, Home/End, `b` (black screen: the whole preview turns black, with a faint “Black screen — press b or Esc to return” hint in the corner for 2 s, and again when the mouse moves; `b` again, Esc, a click, the arrows, Space, PageUp/PageDown or Home/End bring it back without moving the slide), `a` and `f` still reach the slides (not in edit mode, where `b`, `a` and `f` do nothing). While an unsaved script holds the preview, a click or key on it shows why, with Save and Revert next to it.


### Viewer input in the presenter view

In the presenter view's current pane, enter the counts in `m-predict`, or use the timer's **+1 min / −1 min** buttons. The stage and the current pane show the same counts and timer extensions; changes on the stage appear in the presenter view too. The next pane shows the author's values. Input fields and controls keep their own keys, so typing a count does not advance the presentation. After a mouse click on a timer button, Space advances as usual.

Counts and timer extensions survive moving forward or back through steps on the same slide. Entering from another slide or jumping to a slide (including the current slide) restores the author's values. Viewer input is ignored in video mode and does not change the script, authored durations, timeline, video or print output.

## Slide list (add, duplicate, delete, reorder)

The **Slides** tab at the left edge of the preview opens a list there (✕ closes it again): every slide in order, with a thumbnail of its final step and its heading. The thumbnails are drawn by the lesson itself in a sandboxed frame behind the list (the same frame rules as the preview; it takes no clicks and is hidden from screen readers); the list, its buttons and its dialogs are part of the editor page. The list remembers whether it was open (in this browser).

- **Select:** click a slide, or use ↑ ↓ Home End in the list; the preview goes to that slide. When the preview moves, the selection follows.
- **Insert slide ▾** inserts after the selected slide either from a template or by a chat AI (**Have a chat AI write it…**, see “Insert slide…” below). From a template: **Title and body**, **Two columns**, **Figure** (a dashed placeholder and a caption), **Section divider** (`sec`) or **Quote** (a `box` with a `cite` line). The editor gives it a new id (`s-xxxxxx`, never one already used in the document) and adds a script section `## Heading {#id}` with a placeholder line for each step, after the previous slide's section. The placeholder lines start with the mark `✎` and the template text is fixed (both are listed in `kit/core/template-text.mjs`), so what is left unchanged is found: the quality check (here and `npm run check`) warns about it (`narrPlaceholder`, `templateText`), and before TTS (the Audio panel, Colab's `tts-job.json`, `tts/synth.py`) and before exporting an Egatari file (editable, play-only, Live; `--portable`, `--play-only`) the editor or the command lists it first. You can go on (**Make it anyway** / **Export anyway**); otherwise TTS reads the placeholder aloud and it goes into the captions and the readable layer.
- **Duplicate** puts a copy of the selected slide right after it, with a new id. Its script is copied; its audio is not, so its steps show **N steps need audio** in the list until you record or make them.
- **Delete** (or the Delete key in the list) asks first, naming the slide, and lists what goes with it: the script section, the audio records in `audio/manifest.json` and their files (files another step still uses stay), and recorded takes not used yet. Like the stale-audio rule (format §5.4), nothing is regenerated or deleted silently.
- **Reorder:** drag a slide in the list, press **↑** / **↓**, or Alt+↑ / Alt+↓ in the list. The ids do not change, the script sections are put in the same order, and the audio stays attached by its key.
- **Undo** (above the list) takes back the last slide action: the lesson, the script, the audio manifest and the deleted audio files are written back from the editor's memory, and unused takes return to the Audio panel. It is offered until the next slide action, until an Egatari file is saved, or until another lesson is opened; if one of the three files changed in the meantime (an edit, an outside tool), it is refused. The files are also backed up in `.cache/edits/` before each action.

After each action the editor writes `deck.html`, `narration.md` and `audio/manifest.json` (only what changed), rebuilds, shows the affected slide and runs the quality check. A screen reader hears what happened (a live region). An Egatari file keeps the change in memory; the next **Save** rebuilds the file (tier B), since saving without rebuilding cannot change the slide structure (format §7.2; the editor's tier-A save refuses with `source-changed` and asks to rebuild). An Egatari file opened for script only (another runtime or registry version) or read-only cannot use these actions. A lesson whose slide keys collide must be fixed first (the action says why). Slides without an id keep their keys; the new and copied slides always get one.

## Script audio (Audio panel)

**Audio** in the toolbar opens a card in the same trusted side panel. It works the same for a folder and for an opened Egatari file. From the top it has three parts (the design is `handoff/audio-flow-2026-10-25.md` of the project notes; backlog #82, #83, #85, #89):

- **A. The lesson's audio** (always on top): one status line and at most one button. The line says how many steps have audio (“No audio yet (8 steps)”, “5 of 8 steps have audio”, “All 8 steps have audio”), how many need their audio updated because the script changed, and how many AI-made steps are still in the old voice after you changed the voice (`inputHash` does not cover the voice, so the panel compares each AI record's `recipe.voice` with the current voice: the choice in the Egatari file, else `voice.json`, else the default; records without `recipe.voice`, and dry-run audio, are not counted). In an Egatari file it adds “Not in the file until you save”. The button is **Make the rest (n steps)** when some steps have no audio, **Update audio (n steps)** when only stale or old-voice steps are left, **Save** in an Egatari file with nothing left to make, and absent when there is no audio at all (B is open instead). The button continues with the method used last: the cloud (it exports the script of those steps, C1), this computer (it makes them), or recording (recording mode opens at the first of them). The method is kept in `egatari.json` as `studio.audioMethod` (`cloud`, `local` or `rec`; written through `updateConfig`, so every other member stays byte for byte); in an Egatari file it is kept only while the page is open. With no method yet, the button opens B.
- **B. How do you want to add audio?** (open at first, folded once every step has audio): **Voice** above the answers (one picker, or **Voice of the explainer** and **Voice of the questioner** for a dialogue, as in New… ②), then the answers **Make AI voice in the cloud (Google Colab)** (the default), **Make AI voice on this computer** (shown only when this browser can make it, i.e. WebGPU in the hosted or served editor; then it is the default; it says the model is downloaded the first time and offers **Make on this computer (n steps)**), and **Record your own voice** (**Open recording mode (r)**, at the first step without audio).
- **C. This step** (the step on screen; it follows the slides, and while it makes or writes audio it stays on its step and says so if the slides moved): the heading “Slide 3 “…” · step 2”, the current audio (“AI voice · 5.2 s”, “Recording · 4.8 s · Needs updating”, “No audio yet”), the buttons **▶ Play**, **Listen with read-aloud**, **● Record (r)**, **Import from a file…**, **↶ Revert** and (only when this computer can make AI voice) **Remake on this computer**, and the step's script (read only; it is edited in the Script panel) with “n points where the animation follows the voice” when it has `{cue}` / `{mark}`.

The details:

- **Current audio.** Plays the step's audio from `audio/manifest.json` (read from the folder or file in the editor page, never from the preview), with **▶ Play**, its kind (**Recording**, **AI voice**, **Imported**), length and source (for TTS: engine, model, voices, seed). A **Needs updating** badge means the script changed after the audio was made, or it is unknown which script it was made from (format spec §5.4: its `inputHash` is `null` or differs from the current script; for a manifest written by an older `tts/synth.py` without `inputHash`, the TTS cache record `audio/seg_<digest>.json` is compared instead). The quality check (its build warnings) and `npm run check` list stale steps too. The step's script is shown for reading aloud: the field grows with the script (up to about half the panel) and can be resized from its bottom-right corner, and in a dialogue lesson every turn is labelled Expert or Novice (the script syntax; the voice pickers say explainer and questioner). **↶ Revert** puts back the audio the step had before the last new take (see below).
- **Record.** **● Record (r)** (and **Open recording mode (r)** in B, at the first step without audio) opens [recording mode](#recording-mode-keyboard-only) at the panel's step: there is one way to record. For a single step, press **Space**, speak, press **Space** again and **Esc**: the panel is back, showing the new take for that step (it stays open behind recording mode). Recording mode shows the script in large type with the level meter beside it, keeps the take used for the step right away, and **↶ Revert to previous** here walks back through the earlier audio of the step (no audio file is deleted).
- **Import a file…** takes a WAV, MP3, M4A, Ogg, WebM or FLAC file (up to 64 MiB; the size is checked before reading). Like a recording, it is used right away.
- **Voice.** One picker per speaking role (one for a single-speaker lesson, Expert and Novice for a dialogue): `bob` and `alice` for a Japanese lesson, Kokoro voices for an English lesson (eight American and British voices, the rest under **More voices**). **▶ Sample** plays a short pre-made sample (`lab/voices/samples/`; no model is loaded). In a working folder the choice is written to `voice.json`; in an Egatari file it is kept while the page is open (changing `voice.json` would force a rebuild on Save), and the audio record keeps the voice that was used. A name in `voice.json` that AI voice on this computer does not have is handled the same way for both languages: the panel says so and TTS uses the role's default voice (`bob` / `alice`, or `am_michael` / `af_heart`); the TTS window refuses unknown names instead of silently picking another voice.
- **Make AI voice on this computer** (B, for every step that needs audio) and **Remake on this computer** (C, for the step) make AI voice in the browser: Irodori-TTS 500M-v3 for a Japanese lesson (with the reading dictionary `tts/yomi.yaml`, applied with the same rules as `tts/yomi.py`; the voices of `voice.json`, `bob` and `alice` by default; seed 0 and 40 steps; the local mlx server also uses seed 0, but the browser draws its noise with another generator, so the waveform is not the same as a local take), Kokoro-82M v1.0 otherwise (`bob` → `am_michael`, `alice` → `af_heart`, or a Kokoro voice name in `voice.json`). Each part between `{cue}` / `{mark}` boundaries is synthesized and post-processed on its own and the parts are joined like `tts/synth.py` does (350 ms between turns), so the take has cue times (`sync: "auto"`). The first time, the editor says what it downloads (about 1.26 GB for Irodori fp16, 2.44 GB on GPUs without fp16 shaders, about 330 MB for Kokoro; later runs read the browser cache) and opens a small window of the editor's site (`lab/tts-helper.html`) that loads the model and does the synthesis on this computer's GPU. That window receives only the text to read (after the reading dictionary) and the voice name, and returns audio. WebGPU is required (a recent Chrome or Edge on a computer), and it is not available in the Offline editor (`file://`): without them the panel does not offer “this computer” at all, and the cloud is the default (the panel does not frame it around WebGPU). Other reference voices need `tts/synth.py`. The engine follows the language of the script, not of the slides: `"lang"` in `voice.json` first, then the script text (mostly English turns in a Japanese lesson read as English), then `<html lang>`; the voices offered and the reading dictionary follow the same choice.
- **Post-processing** is the same as `tts/core.py`, in the browser (`kit/core/audio-core.mjs`): mono, 44.1 kHz, leading and trailing silence trimmed (−45 dB over a 20 ms window, 50 ms kept), loudness set to −20 LUFS (EBU R128 integrated loudness, one linear gain; where ffmpeg's loudnorm would switch to dynamic processing because the true peak would pass −1.5 dBTP, the gain stops at −1.5 dBTP instead). Because of that difference the profile has its own name, `trim-45-loud-20-cap-v1`. `tools/test-audio-core.mjs` compares lengths and loudness with `tts/core.py` on the same input.
- **Text pre-processing** (`kit/core/tts-normalize.mjs`, rule `join-num-counter@1`) is applied to each part just before it is sent to the engine, in the browser and in the Colab notebook (`colab/egatari_tts.py`, same rule, cross-checked with shared examples): the ASCII or full-width spaces between an Arabic numeral (0-9, ０-９, decimals like 1.5 included) and a following Japanese character (hiragana, katakana, kanji) are removed, so “1 歩” is read as “1歩” and not “ichi po”; “3 分”, “10 本” and “2 つ” are joined, while “x 2 y”, “Chapter 3 is” and the space before a numeral (“第 3 章”) are left alone. There is no table of counter readings. This is how the audio is made, not what is said: `ttsParts` and `inputHash` are not changed, and the take's recipe records `"textNormalize": "join-num-counter@1"` (format spec §5.4). Audio without the field (everything made earlier) is **not** stale and keeps playing, and the panel does not list it: remake a step (**Remake on this computer**, or the cloud) if you hear a wrong reading.
- **Writing a take** (right after recording, importing or TTS) encodes it as MP3 (LAME, 64 kbps CBR, mono, 44.1 kHz) and writes `audio/<rec|tts|imp>_<hash>.mp3` and the step's record in `audio/manifest.json`. The MP3 encoder is not part of the editor's code: it is the unmodified `lame-wasm` file in `vendor/lame-wasm/` of the editor's site (LAME is LGPL; see NOTICE), loaded only when a take is encoded. The the Offline editor has no MP3 encoder and saves takes as WAV (16 bit, larger files); so does the hosted editor if the encoder cannot be loaded. An MP3 starts 1105 samples (576 encoder + 529 decoder delay, 0.025057 s) late; that is written as `startOffset`, and the runtime starts the audio at that time so that `dur` and the cue times stay aligned (the previous manifest goes to `.cache/edits/`; earlier audio files stay, like `tts/synth.py` leaves old wav files). The record says where the take came from: `kind` (`recorded`, `tts` or `imported`), `inputHash` (the script the take was made from, at the time it was made), and for TTS a `recipe` (`engine`, `model`, `voice`, `seed`, `dictionary` = SHA-256 of the reading dictionary), and for every kind `processing` (`trim-45-loud-20-cap-v1`) and, for MP3, `startOffset`. No device name, original file name or other capture detail is recorded. Recorded and imported takes have no cue times (`sync: "none"`, cues empty): cue-driven motion and emphasis then advance by time. The step's length follows the new audio (`dur` in the manifest; the runtime computes the timeline from it); a `dur` override in `timeline.json` still wins, and the panel warns about it. If the take cannot be written (a read-only file, or you declined the editing prompt), it stays in memory under **Audio not used yet** with **Use this take**, until you use it or open another lesson. The previous records for **Revert to previous** are also kept in memory only (up to 20 per step, until another lesson is opened). `tts/synth.py` keeps recorded and imported takes (`--replace-recorded` replaces them).
- **Listen with read-aloud** (no audio file is made). Reads the current step's script with this device's read-aloud voice (the preview of format spec §5.6). `{x|y}` readings read y, and `{cue}`, `{mark:…}` and `@x-` lines are not read; Japanese gets the same reading dictionary (`tts/yomi.yaml`) and text pre-processing (`join-num-counter@1`) as the AI voice (`kit/core/read-aloud.mjs`, shared with the player). **Listen to the selected word** reads only the word or text selected in the script field (with the step's `{x|y}` readings; the same entry point `readAloud(text, lang)` in `app/read-aloud.js` is what the Pronunciation button, #101, will use to try a reading). While it reads, the panel shows “Reading aloud”; **■ Stop**, moving to another step or closing the panel stops it. Only voices that run on the device (`localService`) are used, never network voices. Without one for the language the panel says so and points to AI voice (the cloud with Google Colab, or this computer). Nothing is written: not the working folder, the Egatari file or the audio records; it is never saved as audio.
- **Egatari files:** a new take changes the in-memory folder; **Save** then writes it without rebuilding (tier A: only the step's audio record, its runtime audio entry and the archived audio change).
- **AI-generated voice.** When any step's audio was made with TTS (`kind: "tts"`), the player shows a small “AI voice” badge in the toolbar (its tooltip: “The audio is AI-generated”), the same sentence in the key list (<kbd>?</kbd>), and one line in the presenter view for those steps; nothing is shown on the slide or with the captions. For imported audio (`kind: "imported"`) the key list and the presenter view say “How the audio was made is not recorded”; recordings are not marked. Every output, including Egatari files and play-only copies, carries the kind in `deck-audio` (format spec §5.2, §7.3).

**Make AI voice in the cloud (Google Colab)** is the default answer in B (most school and office PCs have no WebGPU). Free Colab (your own Google account) makes the same voices, and the editor imports the result with cue times. The three steps are buttons with a short note each, and a step that is done gets a ✓ (for this page only).

1. **C1 Export script.** Exports the steps that need audio (no audio, stale, or made in the old voice). The model files come from Hugging Face. The panel lists the steps, the same text as the top of the notebook (`COLAB_STEPS` in `kit/core/colab-core.mjs`): ① press “Connect” at the top right (the notebook is set to a T4 GPU); if it says it cannot connect, Runtime → Change runtime type → “CPU”, then Connect again (CPU works too, only slower); ② Runtime → Run all; ③ when asked to choose a file, choose the exported file; ④ when it finishes, a ZIP file of the audio is downloaded. Only the T4 timing is given (“about 20 s for 10 steps on a T4”); a CPU figure will be added once it has been measured. Japanese uses Irodori-TTS 500M-v3 (ONNX, pinned revision), other languages Kokoro-82M. Cell 1 picks one of two pinned version sets from the CUDA libraries it finds: `cuda13` (onnxruntime-node 1.30.0, @huggingface/transformers 4.3.1, onnxruntime-gpu 1.31.0) when `libcublasLt.so.13` is there, `cuda12` (onnxruntime-node 1.24.3, @huggingface/transformers 4.2.0, onnxruntime-gpu 1.26.0) when only `libcublasLt.so.12` is, and `cuda13` without a GPU; it prints the choice as `env: CUDA libraries … → pin set …`. The two sets give audio that is close but not bit-identical, so a step may sound slightly different when it is made again on another Colab image. If the GPU still cannot be used, the notebook prints one line saying it uses the CPU instead, with the reason, and carries on more slowly. The `env:` lines at the top of cell 1 (Python, Node, GPU and CUDA, the CUDA libraries found, the pin set and its versions) and the `providers in use` line of cell 3 show which path ran; include them when you report a problem (the versions are in `COLAB_PINS` of `tools/make-colab-notebook.mjs`). The notebook starts one long-lived Node worker (`colab/irodori_node.mjs`) that loads the six ONNX sessions and the tokenizer once, then synthesizes one segment at a time (same seed and steps per segment, so each segment is deterministic); the model is downloaded with `local_dir` so the files are real (not Hugging Face cache symlinks, which onnxruntime-node refuses), and a failing install, clone or Node call stops with the last 30 lines of its error output. It post-processes each like the editor does (`trim-45-loud-20-cap-v1`), puts 0.35 s between turns and measures the cue times from the real audio. Without a GPU (or after the fallback to the CPU) Japanese uses a CPU profile: fewer diffusion steps (`IRODORI_CPU_STEPS` in `colab/egatari_tts.py`, 16 against 40 on the GPU) and the fp32 weights (`onnx/`, faster than fp16 on the CPU); cell 1 says so in its `env:` line (`… · CPU（Irodori の steps=16）`). The worker encodes each reference voice once and reuses it (same audio, less time per segment). Cell 4 prints its own times, from a monotonic clock around the real synthesis: each progress line shows the step's time and the running total (`3/10 s-intro:2  (+41.2 s, total 2:15)`), and the last line the total; trust these rather than Colab's cell timer, which can be wrong for long runs. Tick `PROFILE` in cell 3 to print the time of each stage (text, reference voice, diffusion steps, decoding, post-processing) for every segment. Its core is [`colab/egatari_tts.py`](../colab/egatari_tts.py), which can be dry-run locally with no model (`uv run --no-project --with numpy --with scipy python colab/egatari_tts.py tts-job.json out.zip --dry-run`); the notebook is generated by `tools/make-colab-notebook.mjs` (`npm run gen`).
   **Your own reference voice (optional, Japanese/Irodori only).** In the notebook's optional cell, tick `UPLOAD` and pick a WAV or MP3 of 3-30 s (one speaker), or give a Drive path in `DRIVE_PATH`. The notebook checks that it decodes, is 3-30 s long and is not silent, converts it to 48 kHz mono (the same as the bundled reference voices) and uses it as the Irodori reference for every speaker of the job; a bad file stops with a message saying why. Leave the cell alone and the built-in voices are used exactly as before. The output format and `inputHash` do not change, and Kokoro ignores it. **Use only a voice you have the right to use** (your own, or the speaker's permission). The file stays in your Colab runtime and is not uploaded anywhere else (it is gone when the runtime is recycled).

3. **C3 Import the audio…** asks for the downloaded ZIP file with a plain file input (no folder picker, so a browser without the File System Access API, such as Safari, can use it) and reads it (`records.json` and `audio/*.wav`). The editor recomputes each step's `inputHash` from the **current** script and compares it (it does not trust the notebook). A step that matches is written like any other take (MP3, `kind: "tts"`, `sync: "auto"` with the measured `cues`, `recipe`, `inputHash`, `startOffset`; the take-over rule of spec §5.3): at once for a folder, in memory for an Egatari file (then Save, by tier A). A step whose script changed since the export is not used: the panel says “Added AI voice to 6 steps. 2 steps were not used because their script changed after you exported it” with **Update audio (2 steps)**, which continues with the cloud for those steps (there is no separate list of such steps any more). A step that is not in the current script, a record that does not hold up (bad path, a cue count that does not match) and missing audio are skipped with a message. A ZIP file made for another lesson (`docId` differs) is refused (“This ZIP file has no audio for this lesson…”, with the other lesson's title when the job carried one). A different reading dictionary or post-processing version only warns. Each record's `recipe` also carries `runtime`, the pin set and the execution provider that actually ran after any CPU fallback (`cuda12/cuda`, `cuda13/cpu`; `none/…` when the set is unknown, `cuda?` when the provider could not be determined), because the two sets and GPU versus CPU give slightly different audio; the import keeps it in the audio manifest's `recipe`, drops a malformed value, and it is not part of `inputHash`, so it never makes a step stale. The same holds for `diffusionSteps` (Irodori's diffusion steps) and `precision` (`fp16` or `fp32`), which the notebook writes for Japanese.

The ZIP file is a download, so it is untrusted. It is read as bytes with limits applied before anything is allocated (ZIP file 512 MiB, 64 MiB per audio file, `records.json` 4 MiB, at most 400 steps; zip64, encryption and unknown compression are refused; CRC-32 is checked). Only `records.json` and `audio/<name>.wav` are read (names are checked), the audio must decode as a real WAV of the recorded length, and nothing in the ZIP file is interpreted as HTML or code (spec §11).

`tts-job.json` and `records.json` (`egatari: "tts-job"` / `"tts-records"`, `v: 1`) are this product's interchange between the editor and the notebook, not part of the format spec. The optional `title` (the lesson title, up to 120 characters) in `tts-job.json` is copied into `records.json` and is used only to name the source lesson when an import is refused. Each step's record in `records.json` has the shape of an audio record of spec §5.2 (`file`, `dur`, `cues`, `kind`, `sync`, `inputHash`, `recipe`). The tests are `tools/test-colab.mjs` (zip reader, job, import plan, hostile archives, the notebook, and the Python core's dry-run when `uv` is available) and `tools/test-colab-app.mjs` (the editor round trip with a ZIP file made by `tools/colab-fixture.mjs`; folder and Egatari file).

## Recording mode (keyboard only)

Lessons with components that declare sounds or implement `events(k)` show **Mute sound effects** in the slide controls. Use Tab to focus it and Enter or Space to toggle it; its pressed state means all component sounds are muted. The browser remembers this choice when local storage is available. Sounds play on forward step playback in talk and learn after a user gesture; the visible content remains available. Recording mode temporarily silences component sounds throughout the session and restores the saved choice when closed.

<kbd>r</kbd> (in the editor page or in the lesson), or **● Record (r)** in the Audio panel, opens a wide screen for recording the whole script with the keyboard alone. It shows the script of the step **in large type** (a dialogue gets Expert / Novice tags; a long text scrolls inside), and the preview narrows to a stage thumbnail beside it and follows the recording cursor, so you can look at the figure while you read. It lives in the trusted editor page like the Audio panel: the microphone, recording, post-processing and writing are never done in the preview, the preview cannot start a recording (a hint from the lesson can only open this screen), and the preview is inert while the screen is open. It opens at the step on screen (from the Audio panel: at the panel's step) and records the steps that have a script, in order. It is the only way to record: the Audio panel's **● Record (r)** opens it, and the panel stays open behind it, so that **Esc** brings you back to the panel with the new take.

**Keep recording** is on by default and remembered on this device. Step changes play no takes or sound effects.

| Key | What it does |
|---|---|
| **Space** | Start / stop recording. On stop the take is post-processed (the same as the Audio panel: leading and trailing silence trimmed, −20 LUFS, mono 44.1 kHz) and **used for the step right away** (kind `recorded`, with “Revert to previous” as before). You stay on the step. Right after the screen opens (or moves to a step) the Space button reads **Getting ready…** until the step is loaded; a Space pressed then is kept and starts the take as soon as it is ready (once, even if pressed twice) |
| **Enter** | While recording: stop, keep and go to the next step. After a take (or on a step that already has audio): go to the next step. With **Keep recording** on, recording starts on the next step after the previous take is processed and saved, only if the next step has no audio or its audio needs updating. A step with current audio waits. With the setting off, every next step waits. On the last step, Enter keeps the take and stops. A step with no audio says so and does not advance |
| **Backspace** | Retake. While recording it throws the take away (nothing is written). After a take it reverts that take with “Revert to previous”, back to the previous audio, ready for a new Space. Only audio recorded in this mode is reverted |
| **←** / **→** | Previous / next step (a take being recorded is stopped and kept first) |
| **C** | While recording, press at each `{cue}` / `{mark}` timing of the script (the timings are shown as chips ①②…; the next one is outlined, a pressed one is checked). The press times become the cues (`sync: "manual"`; the time is the raw press time minus the silence trimmed from the head). If the number of presses differs from the number of timings, no cues are written (`sync: "none"`, a warning is shown, and figures advance by time): a wrong sync is never made |
| **Esc** | Close (while recording it throws the take away; **Shift+Esc** closes every open card). Focus returns to where it was |

One step is **Space → speak → Enter**. A new take never reuses the cues of the earlier take (spec §5.3): it starts with `sync: "none"` and no cues, and C fills them in. A step whose audio is stale (the script changed) shows a stale notice; a step with timings but no placed cues shows “figures advance by time”. A dialogue is one take per step (one person voices both roles, or two take turns). The meter shows the input level and the elapsed time (a take stops at 600 s and what was recorded up to then is used), the screen says the length of the take and the gain applied, and warns when the input was so loud that it may have clipped. Capture runs for another 0.15 s to receive delayed samples. Before trimming silence, the stop key’s press is cut from 30 ms before keydown; the start is cut through 30 ms after keyup (at least 120 ms after keydown). Enter uses the same cuts for the end of one take and the start of the next. The microphone stays open (one permission, no delay at the start of a take) until the screen is closed, then it is released. The editor never writes if the write is refused (a read-only file, a declined editing prompt): the take stays under “Audio not used yet” in the Audio panel.

For screen readers the screen is a modal dialog; a live region announces the step (n of N, title, whether it has audio, how many cues), “recording”, “Recording continuously: step 3 of 7” while continuing, each cue pressed, and the result of a take, and an alert region reports problems. Every key also has a button (with its key shortcut), and `prefers-reduced-motion` makes the meter update only a few times a second. While the screen is open, <kbd>e</kbd>, <kbd>n</kbd> and <kbd>r</kbd> do nothing, and the toolbar is inert.

Draft, experimental (spec §3.8 draft): the allowed formats per role and the content checks are those of the [reference](reference.md#single-file---portable).

**File ▾ → File info…** shows the title, license, creators, copyright and attribution from `metadata` in `egatari.json` (read only here; edit `egatari.json` in a working folder), the format (“Format: Egatari 1.0 (Working Draft …)”: the file's `version`, with the snapshot of the spec copy in `vendor/egatari-spec/SOURCE.json` when it has one) and the Studio that made the file (“Made with Studio 0.4.6”, from `generator.version`; for a working folder “This Studio: …”), with the note “Playback uses the player inside the file. Edit with the latest Studio.”, and under them the attachments (headed “Attachments (draft, experimental)”). A file the format does not allow is refused with the reason and the rule (§3.8): by its name before the title prompt (executables, the extensions operating systems run as scripts such as `.js`, `.bat` or `.ps1`, HTML, SVG, ZIP, macro-enabled Office files and legacy .doc, .xls and .ppt files, audio and video, any format no role takes), by its content after reading and before writing (a PDF with JavaScript, automatic actions other than going to a place in the document, or actions other than `GoTo` and `URI`, an encrypted PDF that needs a password, an Office file with macros or external references, a renamed executable, a file of two types, audio or video). Values that a spreadsheet may read as formulas are noted but added. Each row has the role (or none: packed but not listed for readers; a role that does not take the file's format is refused), the title (required: a file without one is packed but not listed; it cannot be cleared), the description (optional, one or two sentences, at most 300 characters, shown under the title in the download list), **Rename…** (a new name is checked like an added file) and **Remove**. Roles, titles and descriptions are written to `egatari.json` (`attachments`; other members kept, a backup in `.cache/edits/`). Names outside `attachments/`, with `..`, reserved or colliding names are refused, and so are files over the limits (10 MiB each, 20 MiB together, 100 files) before they are read. Removing a file from a folder keeps a backup in `.cache/edits/`. The editor never opens an attachment and never passes it to the preview. In an Egatari file the changes are in memory until **Save**, which is a tier A save: only the attachment entries of the index, their chunks and the source hash change. Before the first change of an Egatari file the editing prompt applies, as for any edit. **Import live results…** adds the results downloaded from a Live as a `data` attachment with a summary; see [Live](distributing.md#live-questions-and-polls-in-class-draft) (after the lesson).

## Egatari files (no folder)

An Egatari file is what `npm run build -- <deck.html> --portable` (or **File ▾ → Save as…** in the editor) writes (into the top of the working folder, named from the lesson title, and it prints the path). It plays like any built lesson, and it carries the slides, script and audio, so the editor can work on it without the original folder. To hand it to others (Google Drive, email, an LMS), see [distributing.md](distributing.md).

- **Open.** Press **Open a file (.ega.html)…** on the first screen or **File ▾ → Open…**, or drop the file onto the first screen. The editor reads the file as bytes and extracts it in a Web Worker with an HTML parser that runs no scripts; the file itself is never loaded as a page, so nothing in it runs during import. Every hash, size limit and path rule of the format is checked first, exactly as `npm run portable -- unpack` does. The HTML is parsed with budgets counted while parsing (elements, attributes, nesting depth), and the source files it carries may hold at most 500 000 tags, so a file of millions of tiny elements is refused before a full tree is built; a read that takes longer than 30 s stops the worker and refuses the file. The build and the code check of an opened lesson (folder or Egatari file) also run in a worker, within the build limits (see [reference](reference.md#build-limits)); a build that takes longer than 60 s stops that worker and fails (`build-timeout`), and the page stays responsive meanwhile. The build reads from the folder only the files it references (at most 8 at a time, each up to its listed size; a file that grew since the listing is refused); a reply from a stopped worker is dropped. Every file is read with its size checked from `File.size` before reading and from the bytes read (`app/bounded-read.js`); `deck.html`, `narration.md` and `comments.json` have fixed limits (32 MiB, 16 MiB, 4 MiB) and a larger one is refused without being read. The source then lives in memory (an in-memory folder); the preview, the editing tools and the quality check work on it as on a folder. Outside changes are not watched (there is no folder).
- **Save.** **Save** writes the same file again when the browser gave a writable handle (Open a file (.ega.html)… or drag and drop in Chrome / Edge; the browser may ask for permission the first time). Otherwise it asks where to save, or downloads the file when there is no save dialog (Safari, Firefox). The document id (`docId`) stays, and Save never sets or changes `derivedFrom`. **File ▾ → Save as…** asks whether to **Save as a new file**:
  - ticked (“Save as a new file (it becomes separate from the original)”): asks where to save and writes the lesson under a new `docId`, with the original recorded as `derivedFrom` (its `docId` and source hash). Copyright, attribution and creators are kept. The open document becomes the new lesson (later saves keep the new id).
  - not ticked: asks where to save and writes the same lesson (same `docId`) to another file.

  A dot (●) before the file name (and after **File ▾**) means there are unsaved changes; leaving the page or opening another file asks first. In every save the license, copyright, attribution and creators, members of the index the editor does not know (at every level: metadata, audio records, archived blobs, parts and themes, extensions) and extension data are kept, and untouched audio is copied byte for byte. The editor may add the settings file (the lesson id and metadata at the root of the source) to a file that lacks it; that changes the source hash, which the save updates anyway.
- **Saving without rebuilding.** When only script (the text of turns, emphasis and timing), audio or the timing overrides in `timeline.json` changed, Save does not rebuild the slides. It rewrites only the parts of the file that the [format](https://github.com/egatari/egatari-spec) lists for such an edit (§7.2, tier A): the changed entries of the runtime script, emphasis, timing and audio data; the changed steps of the text layer that is readable without JavaScript; the source hash and the archive index with its hash; the archived files (new content added, content that nothing refers to any more removed); and, only when the new text uses characters the embedded fonts lack, a new font supplement (a style element with just the font files that cover those characters, from the editor's own font files; the fonts already in the file are not touched). Every other byte of the file stays exactly as it was, including runtime code written by another tool or another version. The status bar says “saved without rebuilding”. Removing all of a step's script also removes that step's audio; the save notice says there are warnings, and the Quality check panel names the step. Timing overrides are copied entry by entry; the runtime computes each step's length from them with the same formula as before.
- **Saving with a rebuild.** When you edited a slide (or anything else outside the list above changed, or the file's compiled lesson and its source disagree), Save rebuilds the whole file from the edited source with the editor's bundled kit, parts and themes, so it plays exactly like the preview. Before saving it warns: **“The slides are rebuilt with the current version of this editor. Slides you did not edit may look different.”**, says why it cannot save without rebuilding, and saves only after **Rebuild and save** (Cancel keeps the changes unsaved). A lesson that has never been saved (made from the AI's output, or a `deck.html` opened on its own) is rebuilt without asking: this editor built it, so nothing else changes. When only the theme changed (**Change theme…**), the dialog says only that: **“You changed the theme, so the slides are rebuilt with the new theme and saved. …”**. When the file carried another player (its index names a player other than Egatari Player), a second dialog, **“The player will change”**, names the file's player and the one the saved file will carry (“This file plays with Other Player 2.0.0. After saving, it will play with Egatari Player 1.0.0. …”); **Save** saves, **Cancel** keeps the changes unsaved and the file as it was (format spec §4.1). A newer version of the same player is not asked about. Known gap: the editor does not yet compare the slides before and after a rebuild; check the preview after saving.

Re-record it or regenerate it in the [Audio panel](#script-audio-audio-panel).
- **File ▾ → Export ▸ → Export working folder…** writes the source, the audio and `audio/manifest.json` to an empty folder you choose (the same files as `npm run portable -- unpack`); a folder that is not empty is refused. The folder then opens, builds and packs like any working folder.
- **File ▾ → Save as…** (for an open working folder) writes the folder as an Egatari file (editable, `.ega.html`). The suggested file name is the lesson title (`metadata.title` in the settings file, otherwise the lesson's `<title>`), made safe for every OS (no `\ / : * ? " < > |` or control characters, no leading dot or trailing dot or space, no reserved name such as `CON`, at most 80 characters and 255 bytes); without a title it is the slides file name. The first time, a lesson id is written to the folder's settings file so that later exports keep it.
- **Files exported from a working folder** (`exportedFrom`, format §3.1). **Save as…** of a working folder (and `--portable` on the command line) marks the file as exported from that folder, with the folder's source hash at export (no time, path or name). When such a file is opened, an info line (not a warning) says: “This file was exported from a working folder (the folder that holds the slide and script files). Editing it here does not change the files in that folder. If you don't have the folder, you can edit and save this file as usual.”, with an **Export working folder…** button (the same as File ▾ → Export ▸ → Export working folder…). Editing is not refused. Save and Save as… keep the marker unchanged, so once the file's source hash differs from it the notice adds “This file has been edited since it was exported.” Save as a new file drops it: a lesson with a new `docId` is not an exported file, and reopening it shows no notice. A lesson that starts in the editor without a folder (pasted, or opened from `deck.html` alone) never gets the marker. The unpacked folder carries no marker and becomes the master; its next export writes a fresh one. With both the file and the folder at hand, `npm run portable -- compare <file> <dir>` says which was edited after the export ([reference](reference.md#single-file---portable)).
- **Not saved into the file:** comments and the backups in `.cache/edits/` stay in memory only (comments are review notes; the format leaves them out).

### Editing prompt (“Edit this file?”)

Each time a file is opened for editing, before the first change (the first save from edit mode or the script drawer, or pressing Edit / Script), the editor shows the lesson's title, creators, copyright, license and attribution as written in the file (they are claims; nothing verifies them). If the license does not permit derivatives (a Creative Commons `-ND` license, or “All rights reserved”), or there is a copyright notice but no license, it warns that modifying or sharing a modified copy may infringe the rights holder's copyright, and editing starts only after you tick the confirmation. Cancel leaves the file unchanged. Saving never removes the copyright, attribution or creators.

### Opening a slides file (deck.html) or a built presentation

- **A slides file** (`deck.html` from a working folder, for example downloaded from GitHub: it has `<section class="slide">` and no built runtime or format blocks) is not refused. The editor explains that its script, audio and own parts live next to it in a folder and offers **Open the folder…** (the folder picker; the folder then opens as usual), **Open this file only** and **Cancel**. *This file only* makes a new in-memory lesson with just `deck.html`: no script or audio; registry parts and themes work, and files it references that are not there (lesson-local parts, `{{JSON:…}}` data, includes, figures) become build warnings, each once, and are left empty (this applies to every in-memory lesson; a folder still fails the build on a missing file). It is treated like any opened file: the code question comes first if the lesson has code, it has a new `docId`, there is no editing prompt (no rights are stated), and a notice says only `deck.html` is open and nothing is saved yet. **Save** asks where: **Save as an Egatari file (`.ega.html`)…** or **Export to a folder…** (an empty folder).
- **A built presentation** (such as `out/deck.html`: the built runtime and `deck-meta`, but no source) is refused with its own message: it is a presentation build; open the working folder (offered as **Open the folder…**) or an Egatari file instead.
- **A play-only Egatari file** (`.play.ega.html`) is refused with a message that names it: it plays in a browser as is; to edit, open the original Egatari file or the working folder. Any other HTML is “not an Egatari file”.

### Files the editor refuses or opens read-only

- **Refused, with the reason:** a file that is not an Egatari file or is play-only (see above), a broken hash or a missing part, a path that is not allowed (e.g. `../`), a duplicate member in the index, a document id that disagrees with the settings file, and a newer source contract.
- **Newer major version, or a required feature the editor does not implement:** not opened for editing and never re-exported. The dialog offers **Export working folder…** to extract the source when the index and the archived data check out with the rules of the version the editor knows; otherwise extraction is refused too. (Such a file may still play in a browser.)
- **Script, audio and timing only:** registry parts or themes whose hash differs from the editor's (or that the editor does not have), and an existing file with an unavailable exact part requirement. The editor cannot rebuild such a file faithfully, so a notice says only script, audio and timing can be edited: Edit (slide text) is refused, the script drawer works, and Save rewrites only those parts without rebuilding. Slide editing, theme switching and replacement are disabled. For an unavailable requirement, the notice names the part and what it requires, and asks you to update the parts to rebuild; the preview keeps the file's own player and plays the remaining parts.
- **Read-only:** a file the editor cannot build for other reasons, and a file of the previous kind whose compiled lesson and source also disagree. The lesson is shown, Save is refused, and Export working folder… works.
- **Its own code:** whether a lesson has code of its own is decided from the built document — the source after every include and preprocessing step, covering every file the build reads as text whatever its extension (an image file included with `/*INCLUDE:…*/` counts), and the same bytes the preview then shows (a `<script>` without `src` whose content is empty or only whitespace is not code; one with only a comment is); the folder is not read a second time to check. Before anything from such a lesson (or a file with the “extended” profile) runs, the editor says so and asks; the preview starts only after **Start the preview** (Cancel leaves the file closed). The preview is emptied before the question, so neither the previous lesson nor anything of the new one is shown or runs behind it. While it is open, a notice stays at the top: the code runs only inside the preview, without network access, and cannot change the file. The same question comes for a folder with parts (`components/…`, any `.js` file) or scripts in `deck.html`, once per opened folder (also when such code appears later).

- **Revise…** **1. What should be changed?** (optional) → **2. Send the fix request to your chat AI** (the quality check findings (the check runs again), what you wrote, the open comments (`comments.json`; resolved ones are left out; images of pins or markers are backlog #90) and the current slides and script; if there is nothing to fix, it says so) → **3. Paste the AI’s output** (the same two fields; “If only the fixed slides are in the output, only those slides are replaced.”) → **Replace**. One field alone is enough (with “The script stays as it is.” or “The slides stay as they are.” beside the button).
- **Copy a fix request for your AI.** In the quality check panel. It writes a fix request to the clipboard (and shows it): the findings (errors and warnings), the standards they break with their text taken from the same instructions (standards have names like `R-title`), the notes of the parts the lesson uses (the same text as the instructions), the amounts of overflow and small text (“cut the body by 97 px (about 3 lines of 46 px)”, “raise the text from 23.2px to at least 24px”), build notes about the script, and the current `deck.html` and `narration.md`. For a long lesson (over 40 000 characters together) it carries only the slides with findings and their script and asks for those slides back. Paste it into the same chat; **Paste the AI’s output…** opens step 3 of **Revise…**.
- **Replacing (Revise…, step 3).** The output goes into the current lesson (not for a play-only Egatari file) and the document is kept: for an Egatari file the `docId`, settings, audio and parts stay and only the source is replaced (unsaved until you save); for a folder `deck.html` and `narration.md` are written with a copy in `.cache/edits/`, and the code check asks again if code appears. An output with only some id'd `<section>`s replaces just those slides and their script sections. With only the script field, only the script is replaced (just the sections, when every section has an id).
- **More in the quality check:** script for a step a slide does not have (an error), the script of static slides such as the cover, and readings `{x|y}` that hold an expression or several symbols (a warning: one reading per symbol or term). The command quality checker has the same three checks.

## Files it writes

Exactly the same as the dev server ([dev-server.md#files-it-rewrites](dev-server.md#files-it-rewrites)), all inside the chosen folder:

- `deck.html`: only the contents of the element you edited
- `narration.md`: only the lines of the step you edited (comments and other lines stay)
- `comments.json`: comments, `[{id, created, key, range, pin, quote, comment, status}]` (`pin` is the clicked point `{x, y}` in slide coordinates, 1280×720; a marker comment adds `strokes`, the drawn marks (older comments may have a single `stroke`), see [contract §13](contract.md#13-review-notes-the-ink-stroke); see the [dev server](dev-server.md#files-it-rewrites). To look at what the comments point at, run `npm run comment-shots -- <working folder>` on the folder: it renders each open comment's step with its pin into `.cache/comment-shots/`)
- `audio/<rec|tts|imp>_<hash>.mp3` and `audio/manifest.json`: with **Use this take** in the Audio panel (only the step's record changes; the previous manifest is backed up)
- with the [slide list](#slide-list-add-duplicate-delete-reorder): `deck.html` (whole slides inserted, copied, removed or moved), `narration.md` (whole sections), `audio/manifest.json` and, when a slide is deleted, its audio files in `audio/` (backed up first; Undo writes them back)
- `.cache/edits/`: the previous `deck.html` / `narration.md` / `audio/manifest.json` before each change (the newest 30; cleanup deletes only files named like these backups, `<time>-<name>`, and leaves anything else in the folder)
- with **Save as…** of a working folder and **For participants (play-only)…**: the file you chose (and, the first time, the lesson id in the settings file of the folder)
- with an opened Egatari file: nothing until you save (edits are in memory); then only the file you chose, or the files in the empty folder of “Export working folder…” (saving without rebuilding rewrites only the parts listed above)

## Limits

- **Chrome / Edge only.** Mobile browsers cannot open folders either.
- **Models for AI voice on this computer.** The model is stored in the browser's cache for the editor's site (Irodori-TTS about 1.26 GB, Kokoro about 330 MB). **Help** shows how much storage the site uses (`navigator.storage.estimate`) and which models are stored, and **Delete models** removes them (audio you made stays; the next use downloads again). When the TTS window loads a model it deletes the caches of older model versions and asks the browser to keep the storage (`navigator.storage.persist`); otherwise the browser may delete the models when the disk is nearly full, and Safari after about a week without a visit.
- **Command line only:** TTS with your own reference voices or the server engines (`tts/synth.py`), video (`tts/`, `render/`), the command quality checker (`npm run check`), `tools/pdf.mjs`. The preview plays the audio in `audio/manifest.json` (folder or Egatari file) when you autoplay (`a`): the editor reads each file and hands its bytes to the preview, which plays them from `blob:` URLs of its own document (the sandboxed preview cannot read the folder or the editor's `blob:` URLs).
- **Audio panel in the editor app only.** The dev server has no Audio panel (open the folder in the editor app, or use `tts/synth.py`). Making AI voice on this computer needs WebGPU and the hosted or served editor.
- **Bigger exports.** The command-line build can subset the Japanese font with fonttools (`node tools/get-fonts.mjs`); the browser cannot, so the editor embeds the matching font files whole (as the command line does without the TTF files). `examples/minimal` is about 2.0 MB from the editor and 0.7 MB from `npm run build` with subsetting. The lesson looks the same.
- **No Mincho in the Offline editor.** The hosted editor includes BIZ UDPMincho (loaded only for lessons that use it, such as theme `kokugo`); the Offline editor `dist/editor.html` does not, to stay small. There a Mincho lesson builds with a warning and shows the Mincho font of the device that opens it.
- **Bundled parts.** Library parts (every version in `vendor/components/`, with `components.lock.json`), themes (`themes/`, with the earlier versions in `vendor/themes/` and `themes.lock.json`) and the runtime (`kit/`) of the repository are the ones bundled when the editor was built. A lesson is rebuilt with the part version whose hash it recorded, when the editor has it, and likewise with the theme version it recorded. When that theme version is not the current one, the preview keeps the recorded colors and the notice above it says so, lists each color that changes in the current version (old → new, with swatches) and offers **Update theme**; only that button rebuilds with the current version (it sets `themes` in `egatari.json` and the lesson's record; Save then writes the new colors). Nothing is restyled silently ([reference](reference.md), “Theme versions”). Parts and themes inside the working folder (`components/<name>/index.js`, `themes/<name>/`) are read from the folder as usual. A theme that is in neither (an institution's theme in your own theme folder, which the command line finds through `EGATARI_THEMES` or `~/.egatari/themes`) builds with `default` and the warning `theme not found: "<name>"`, and the notice above the preview offers **Load theme…** (also in the warnings panel)
- **Load theme.** **Load theme…** (in the theme notice, at the end of the theme list in New… (step 3), and in **My themes…** on the first screen) opens a small dialog, **Load theme**: “Load a theme from a ZIP file or a theme folder.”, with **Choose ZIP file…**, **Choose folder…** (only in browsers that can choose folders: Chrome and Edge) and **Cancel**. The file or folder picker opens from that button, so it works on the iPad too.
- **Your theme folder.** **Choose folder…** lets you pick your personal theme folder once, for example `~/.egatari/themes` (in the macOS picker, ⌘⇧. shows hidden folders). The editor then looks for themes in the same order and under the same containment rules as the command line: the working folder, its `themes/`, this folder, the bundled themes; a theme's files, logos and `extends` parent must stay inside its own root (or the bundled themes). The folder is opened read only and the editor never writes there; its contents are treated like lesson files (theme CSS goes through the same sanitising, logos become data URIs), and only the files of the themes a build uses are read. The browser keeps the folder handle in IndexedDB (not the contents) and asks for permission to read it again the next time it is needed: the notice then offers **Use theme folder “<name>”**. **My themes…** shows the current folder and its themes, and **Forget this folder** forgets it. Exporting or saving an Egatari file stores the user theme it used as the lesson's `themes/<name>/`, so the file rebuilds with the same theme elsewhere (an Egatari file made with `npm run build -- --portable` already carries it there)
- **Themes from a ZIP file (My themes).** In every browser, including Safari, Firefox and the iPad, which cannot choose folders, **Choose ZIP file…** loads themes from a `.zip` file. Every folder in the ZIP file, up to 5 levels deep, that contains `tokens.css` is a theme named after that folder (a `tokens.css` at the top of the ZIP file takes the file's name), and all of them are loaded, so `extends` between themes in the same ZIP file resolves. Only `tokens.css`, `theme.json`, the logos its `logos` lists inside the theme folder and top-level `LICENSE*` files are read. The ZIP file is treated as untrusted: at most 32 MB, 3000 entries and 16 MB of theme files (tokens.css 4 MB, theme.json 64 KB, each logo 4 MB); an entry with `..`, an absolute path or a symbolic link, or a theme name that is not a single lowercase identifier (`^[a-z][a-z0-9-]{0,63}$`), refuses the whole file with a message that names the entry and says what to do. The themes are saved in this browser (IndexedDB, contents included, one record per theme name) and appear under **My themes** in the theme list. Loading a theme whose name is already there replaces it: “A theme named “<name>” was already there; it was replaced with the one you just loaded.” **My themes…** on the first screen lists each saved theme by its display name with its own **Delete**, which asks first (“Delete “<name>” from this browser. The ZIP file you loaded is kept.”). A lesson whose theme was deleted builds with `default`, and the notice says the theme is not among the themes saved in this browser and to load it again with **Load theme…**. The build reads saved themes at the same place as the theme folder, in the same order and under the same rules; when the theme folder and the saved themes have a theme with the same name, the one chosen or loaded last is used (choosing such a folder says “A theme named “<name>” is also saved in this browser; the one in the folder is used.”). To make a theme ZIP file, compress the theme folder (on a Mac, **Compress** in the Finder's context menu; on Windows, **Send to → Compressed (zipped) folder**), or use **Code → Download ZIP** on a GitHub repository of themes
- **Not read:** names starting with `.`, and the `out/`, `audio/`, `video/`, `bundle/` and `node_modules/` folders (up to 3000 files, 10 levels deep). `audio/` is read only to save an Egatari file.
- **Rebuilds are not compared yet.** A save that rebuilds (after a slide edit) builds the whole file again with the bundled kit, so a file made by an older or newer build changes outside the edited parts, and fonts are embedded whole. The editor does not yet show which slides changed besides the edited ones.
- **Font supplements err on the side of more.** For a file whose subset fonts declare no `unicode-range` (made on the command line by an earlier version), the editor knows only that the characters of the original script are covered, so it may add font files for characters the subset already had (the file grows a little; it never lacks a glyph).
- **Network in the lesson is blocked.** External images and scripts (`https://…`) do not load in the editor's preview; the build warns about them anyway.

## How it works and security

- **One build for both.** `kit/core/build-core.mjs` is the build (annotation, includes, KaTeX, parts, script, emphasis, timing, themes, assets, fonts) with no Node dependency; it reads files only through an interface it is given. `kit/build.mjs` passes Node's file system (plus fonttools subsetting and ffmpeg); the editor passes the chosen folder and the bundled kit, parts, themes, KaTeX and fonts. With font subsetting off, both produce byte-identical HTML (`tools/test-app.mjs` checks this for `examples/minimal` and `examples/tmlr2026-calibration`). The script parser and the script rewriting (`kit/core/narration-core.mjs`) and the New… template (`kit/templates/new-deck.mjs`) are shared the same way.
- **One editing UI for both, outside the lesson.** `server/editor-ui.js` (the source card, the script drawer, the comment box and list) runs in the editor page here and in the dev server's frame page. It sends the same requests (`/__dev/source`, `/__dev/edit`, `/__dev/narration`, `/__dev/comment`, …): the dev server answers them over HTTP, the editor answers them in the page against the folder (`app/devapi.js`). Inside the lesson there is only `server/hints.js`, which sends hints (see below).
- **The lesson runs in a sandbox and cannot write.** The preview is an `<iframe sandbox="allow-scripts allow-modals">` without `allow-same-origin`, so the lesson has an opaque origin: it cannot reach the editor page, its storage or the folder handles. `allow-modals` is there for printing. On top of the page's Content-Security-Policy (which allows loading only the editor itself and no frame navigation, `frame-src 'none'`), the preview document gets its own policy in force before any byte of the lesson is parsed: the editor builds the document as a trusted prefix (doctype, `<html><head>`, `<meta charset>`, the policy `<meta>` and a small trusted shim) followed by the built lesson unchanged, and never searches the lesson's markup for a place to put the policy. The policy is `connect-src 'none'`, images, fonts, styles and media only from `data:` / `blob:` (the build embeds them), no workers, frames, forms or `<base>` (the preview policy keeps `'unsafe-eval'` only for yanked part versions, below). The presenter view is a window the editor opens, with the lesson again in a sandboxed iframe under the same policy; the editor relays its messages.
- **The editor page forbids eval; yanked part versions are the only reason a policy ever allowed it.** The page's own Content-Security-Policy has no `'unsafe-eval'` (only `'wasm-unsafe-eval'`, which the MP3 encoder's WebAssembly needs and which allows no `eval` or `new Function`; the hosted editor and the single-file `editor.html`; a test listens for CSP violations on the page). Components v1.0.0 and v1.0.1 let `m-sweep` and `m-curves` run formulas with `new Function`; the registry has withdrawn (yanked) those versions with v1.0.2 as the replacement ([SECURITY.md](../SECURITY.md#components-yanked-by-the-registry)). When a lesson records a yanked version, the editor shows a notice and a button **Rebuild with 1.0.2** and never replaces the version by itself (spec §6; rebuilding can change the parts' identity hashes and what is drawn: the note after the rebuild lists which hashes changed). Until then the lesson still plays, only inside the preview frame, which is a sandbox without `allow-same-origin` (an opaque origin that cannot reach the editor page, its storage or the folder handles). The frame inherits the editor page's policy, so inside the editor a yanked `m-sweep` or `m-curves` cannot evaluate its formula and shows its inline placeholder (`DECK.componentErrors`) while the rest of the lesson plays; the preview policy (`PREVIEW_CSP`) and the dev server's lesson document (a top-level sandboxed document, no editor page around it) keep `'unsafe-eval'`, so yanked versions do run there.
- **Hints, not requests.** The preview has no way to ask for a write. It sends only hints: “edit the element with this `data-src` range and hash” (double-click in edit mode), “a comment at this element” (Alt+click; the slide and step key, a short quote of the element, the text near the point and the point in slide coordinates), the keys `e` / `n` / `c` / `r` / Esc (`r` only opens the recording screen), and its position (`deck-pos`). A hint carries no text to write. The editor checks the source window and the shape of each hint, ignores an edit hint outside edit mode, reads the current source itself, checks that the range is an editable element of the current build and that the hash matches, and shows its own card; it writes only when you press Save or ⌘/Ctrl+Enter in that card or drawer. The editing prompt and read-only mode apply to these writes as before. The editor sends the preview only what it needs to show: edit mode on/off, the element to highlight, “go to this step”, print and quality check. The point of a comment is checked as in the dev server (numbers only, clamped to the 1280×720 slide, other fields dropped; `app/devapi.js` checks it again with `kit/core/comment-core.mjs`); a forged point only moves the marker, and the markers over the preview are drawn by the editor page from the preview's own size.
- **The editor touches only the folder or file you chose**, and only after the browser's permission prompt.
- **A save stays with the lesson it started on.** After every wait (rebuild, a question, the permission prompt, the save picker, creating and writing the file) the editor checks that the same lesson is still open, and carries that check into the write itself: if another lesson was opened meanwhile, the file is not replaced (the write is aborted) and nothing else is written. A new lesson id is written to the lesson's settings, and the lesson marked saved, only after the file has been written. An edit made while a save is in progress keeps the unsaved mark, because the saved file does not contain it.
- **While you edit in a trusted field** (a source or comment box is open, or you are typing in the script drawer or it has unsaved changes), the preview is `inert`; hints from the lesson then neither open, close nor switch panels, and the script step you are editing does not change.
- **Folders and links.** In-memory and OPFS folders cannot contain symbolic links. In a folder you pick, Chromium does not show links to the editor at all (they are not listed, cannot be opened by name and cannot be written; `tools/test-security.mjs` checks this), so the build cannot read a file outside the folder through one. The File System Access API gives the editor no way to tell links apart itself, so this relies on the browser.
- **Microphone and TTS only in the editor page.** Recording (`getUserMedia`, `MediaRecorder`), importing, post-processing and MP3 encoding run in the editor page; the preview cannot start them, and no audio is taken from the preview. Recording happens only in recording mode; the preview is `inert` while it is open, and while the panel makes or writes audio hints from the lesson do not switch its step. The page's policy still allows no network: AI voice on this computer is made in a separate window of the same site (`lab/tts-helper.html`, which, like the lab page, loads pinned libraries from jsDelivr and the model from Hugging Face) that is sent only the text to read and the voice name; the editor accepts audio only from that window, checks its sample rate and length, and processes it like a recording. Audio read from the folder is size-limited (manifest 16 MiB, each audio file 64 MiB).
- **Opening an Egatari file runs nothing from it.** The file is read as bytes and parsed in a Web Worker (bundled into the editor; the page's policy allows workers only from `blob:`) with the same parsing rules as a browser with scripting enabled (nothing is executed); the editor never navigates to it or inserts it into a page. Only the lesson rebuilt from its source runs, in the same sandboxed preview as a folder.

## Publishing on GitHub Pages

`.github/workflows/pages.yml` builds `dist/` with `node tools/build-app.mjs --out _site` and deploys it to GitHub Pages: the editor at the root (`/`), the Offline editor at `/editor.html`, the lab page at `/lab/irodori.html`, and at `/editor/` a page that redirects to `/` keeping the query and `#` (the editor used to live there). All paths are relative, so the same files work at the custom domain <https://studio.egatari.org/> (set in Settings → Pages → Custom domain, covering the whole site) and at <https://egatari.github.io/egatari-studio/> (which redirects to the custom domain). Only release tags deploy: pushing a tag `vX.Y.Z` (three numbers; `v0.5.0-rc.1` and other rc tags do not), or running the workflow on such a tag to deploy that release again. Pushes to `main` and pull requests only build (so a broken build shows up before a release), and running the workflow on a branch is a dry build. The release steps are in [RELEASING.md](../RELEASING.md). It deploys nothing until Pages is set up:

1. Settings → Pages → Build and deployment → Source: **GitHub Actions**.
2. Settings → Secrets and variables → Actions → Variables: add `EDITOR_PAGES` = `true` (without it, builds still run but nothing deploys).
3. Settings → Environments → `github-pages` → Deployment branches and tags: add the tag rule `v*.*.*` (the environment allows only `main` by default, and a deploy from a tag is refused without it).
4. Push a release tag, or run the workflow on one (Actions → pages → Run workflow, choose the tag).

The build also writes the samples as Egatari files to `examples/<name>.ega.html` (`tools/examples-portable.mjs`, about 14 MB together; `--no-examples` leaves them out), and the editor's first screen lists them. They are built from a temporary copy of each sample folder (nothing is written into `examples/`); a sample without `egatari.json` (such as `minimal`, which may be copied as a template) gets a `docId` derived from its name, so every build is the same document.

### Release assets

`npm run release:assets` (`tools/release-assets.mjs`) builds the same sample files into `out/release/` with an `examples.json` (name, title, language, slides, size, sha256). It uploads nothing; attach the files to the GitHub release by hand, for example `gh release create v<version> out/release/*.ega.html`.

### Versions (frozen copies)

The site keeps every release from v0.4.1 on: the root serves the latest release, and `/vX.Y.Z/` (for example <https://studio.egatari.org/v0.4.2/>) a frozen copy of that release with the same layout (`/vX.Y.Z/editor.html`, `/vX.Y.Z/lab/…`, `/vX.Y.Z/examples/…`). Since Pages deploys one artifact, the release deploy assembles it (`node tools/site-versions.mjs assemble`): the new build at the root and at `/v<its version>/`, and for each earlier published release the asset `editor-site-vX.Y.Z.tar.gz`, downloaded, checked against the line `editor-site-vX.Y.Z.tar.gz sha256: <hex>` in the release notes (and GitHub's own digest of the asset) and unpacked under `/vX.Y.Z/`. A release without the asset (v0.4.0 and earlier) is skipped; a missing or wrong sha256 fails the build. The asset is the built `dist/` packed reproducibly (`node tools/site-versions.mjs asset vX.Y.Z` builds it from a git worktree at the tag, after `npm ci`); it is attached at release time ([RELEASING.md](../RELEASING.md)). `versions.json` at the root lists the versions; pushes to `main` and pull requests run the same assembly as a dry build. At about 50 MB a version, the 1 GB limit of GitHub Pages holds about 18 versions; the assembly warns above 800 MB and fails above 1 GB.

- **Notice and list.** A copy shows a line at the top: “You are using Egatari Studio v0.4.2, a frozen copy of that release”, a link to the latest version (the root, keeping `?lang`), and a list of the other versions; ✕ hides it. The root lists the versions below its first screen. Copies built before this notice existed (v0.4.1, v0.4.2) get it from the root's `version-notice.js`, which the assembly adds to their `index.html` and `editor.html` (one `<script>` after the policy `<meta>`; nothing else in a copy is changed).
- **Shared browser data.** All versions are one site (one origin), so they share the browser's data: the recent files list (IndexedDB `motion-slides-editor`; it holds only file handles and names, and every version reads it the same way, so a file opened in one version is listed in all), the UI language (`localStorage`), the user theme folder, and the models for AI voice on this computer (Cache Storage, named by model revision, so versions with the same model share the 1.26 GB download). Only the root removes caches of other model revisions; a copy never does (`inFrozenCopy` in `lab/model-cache.mjs`), but the copies v0.4.1 and v0.4.2 predate this rule and would remove a newer model if a later release changes it. A future change to the recent-files store must use a new database name, since older copies keep opening it. There is no service worker; the web app manifest's scope is each copy's own folder.

## Language

The editor follows your browser language (Japanese or English). Switch with the **English / 日本語** button at the top right, or open `…/?lang=en` or `?lang=ja`. The choice is remembered; switching while a lesson is open reopens the same folder (an opened Egatari file is closed; unsaved changes are asked about first). The editing tools (edit mode, the source card, the script drawer, comments) follow the editor's language. (In the dev server they follow the lesson's language, `<html lang>`.)
