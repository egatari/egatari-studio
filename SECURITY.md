# Security

## Trust model: a deck is code

Treat a deck folder like a source-code repository, not like a document. Build, check, render or serve only decks you trust.

- **Scripts run.** Inline `<script>` in `deck.html`, components (`components/<name>/index.js`, deck-local ones first) and component attribute expressions run in the browser that opens the built HTML, and in the headless Chrome used by `kit/check.mjs`, `tools/pdf.mjs`, `render/` and the tests (Playwright).
- **Build reads local files, inside the deck folder only.** `/*INCLUDE:…*/`, `{{JSON:…}}`, `{{FIG:…}}`, `narration.md`, `timeline.json`, `macros.tex`, `audio/manifest.json` and referenced assets (`<img src>`, `<link rel="stylesheet">`, CSS `url()`, …) are resolved relative to the deck folder (`INCLUDE` also searches `kit/`). Paths that leave the folder, through `../`, an absolute path or a symbolic link, are refused with a warning (`refused: …`) and nothing is read. Since 0.2.2 the same check covers components and themes: a deck-local `components/<name>/index.js` must be inside the deck folder (a repository component inside `components/`), and a theme's `tokens.css`, `theme.json` and logos must be inside the theme's own folder and inside its authorized root (the deck folder or `themes/`). A deck's `<html data-theme>` may only name a theme in the deck folder or in `themes/`, and every `extends` parent, at any depth, is held to the same root, so `extends` cannot leave it through `../`, an absolute path or a symbolic link (nesting stops at 16 levels). A theme that is refused falls back to `default`. A `--theme` given on the command line is trusted, and its parents are looked up in its own folder or in `themes/`. (Up to 0.2.1 this sentence was not true for components, theme files and `extends`.)
- **Build output is self-contained.** Local assets are embedded as data URIs. `http(s)` references are left as they are, and the build warns that the deck is then not fully offline.
- **The dev server is local-only.** `server/dev.mjs` listens on `127.0.0.1` only, accepts only `Host: 127.0.0.1:<port>` or `localhost:<port>` (against DNS rebinding), and writes (text edits, narration, comments) need JSON, a same-origin request and a per-run token. It writes only inside the deck folder (`deck.html`, `narration.md`, `comments.json`, `.cache/edits/`): since 0.2.2 a save is refused (HTTP 403, nothing written) when the file or any folder between the deck folder and the file is a symbolic link, even one that points inside the folder or points nowhere, and files are written to a temporary file and renamed into place. It reads the deck, narration and comments only when their real path is inside the deck folder. Pruning old backups deletes only regular files whose names have the backup form (`<timestamp>-<name>`) in a `.cache/edits/` that is not a link; other files there are left alone. (Up to 0.2.1 these writes followed symbolic links, and pruning could delete any file in the folder `.cache/edits` pointed to.) Do not expose it to a network or put it behind a proxy.
- **Build output and TTS output.** `node kit/build.mjs` writes `out/<name>.html` inside the deck folder only through folders and a file that are not symbolic links; with `-o` outside the deck folder it creates that folder and does not write through a link at the file itself. `tts/synth.py` stops before writing when `audio/`, `.cache/voices/` or a file it writes there (`seg_*.wav`, `seg_*.json`, `manifest.json`, the temporary files) is a symbolic link.
- **The editor app** (`dist/editor`) also prunes only backup-named files in `.cache/edits/` (since 0.2.2). It reads and writes the folder through the browser's File System Access API. In Chromium on macOS we checked that symbolic links inside the chosen folder are not listed, cannot be opened by name and cannot be written, so the app does not follow them; other browsers and operating systems have not been checked.
- **Deck code can edit its own source while you edit it.** In the dev server and in the editor app, the editing UI runs inside the deck page, so code in the deck (an inline script or a component) can send the same edit requests as the UI: it can rewrite `deck.html`, `narration.md` and `comments.json` of the deck you opened (nothing outside that folder; the previous version is kept in `.cache/edits/`). Open for editing only decks, and copy into your deck only components, that you trust. Version 0.3 moves the editing UI out of the deck page so that the deck can no longer authorize writes.
- **TTS and video** (tier 2) send narration text to the TTS server in `IRODORI_URL` (default `http://localhost:8882`). Point it only at a server you run or trust.

### What is not covered

These still follow symbolic links or are not checked. They matter only for a deck folder you did not create yourself; the advice above (build or serve only decks you trust) is the protection:

- `render/render.mjs` and `render/export-canon.mjs` write into (and delete old `clip_*` files from) the `--out` folder you pass, and follow links there. Do not point `--out` into a folder from an untrusted deck.
- `tts/synth.py` reads `narration.md`, `voice.json` and the deck without a containment check, and a reference voice named by path in `voice.json` may be anywhere on the machine (it is sent to the TTS server, by design).
- `tools/pdf.mjs`, `tools/shot.mjs` and other tools write where you tell them to.
- A race in which another process swaps a folder for a link between the check and the write is not prevented (the threat is a link that ships with a deck, not a process running at the same time).
- The symbolic-link tests are skipped on Windows (creating links needs privileges there); junctions are treated as links by the same check but this has not been tested.

`comments.json`, `.cache/`, `.env*` and `*.local.json` are gitignored so that review notes, edit history and local settings are not published by accident.

## Reporting a vulnerability

Please report security issues privately through GitHub's **Report a vulnerability** button (Security → Advisories) on <https://github.com/moiku/motion-academic-slides>, rather than in a public issue. Include the affected file or command, a minimal deck that reproduces it, and the impact. You should get a reply within two weeks. There is no bug bounty.
